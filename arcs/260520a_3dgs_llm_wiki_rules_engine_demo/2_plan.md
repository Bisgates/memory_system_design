# 2_plan — LLM-Wiki 规则引擎最小可运行原型

> Generated by /arc-plan. Free-form; provides the route map for /arc-execute.
> After each step, append `arc log "..."` (writes to the `## log` section of 0_meta.md). When the plan does not anticipate the situation, stop and ask the user.

## Strategy

把 wiki 视作 `(atoms, rules) → derived` 的纯函数：atoms 是从 source markdown 用确定性规则抽出的事实，rules 是用户撰写的 `pattern → action` markdown 页，引擎 forward-chain 到 fixpoint。

为了让"指数增长 vs 线性增长"成为可证伪的实验，刻意走两步：先用 **10 条 seed rules** 跑一遍记 baseline，再加 **第 11 条 rule**（这条要刻意挑能跟前 10 条链式触发的 pattern，比如 derived atom 又被另一条 rule 消费），看边际 yield。第 11 条若仅产生 0-1 条 derivation，说明 rules 之间不组合 → 抽象证伪。

**整个 demo 在 arc 沙箱里完成**：源数据只读（不修改主项目 `docs/` 或 `wiki/`），引擎代码在 `utils/`，一次性脚本在 `scripts/`，wiki 产物在 `output/<ts>/wiki/`。

## Steps

1. **Design atom schema + rule DSL (doc/)**
   - input: 8 篇 `arcs/all/*/9_summary.md` 的真实形态
   - output: `doc/atom_schema.md`、`doc/rule_dsl.md`
   - acceptance: schema 能覆盖 (i) entity / (ii) (subj, pred, obj) triple / (iii) provenance / (iv) derived_from 反向链。rule DSL 至少支持 conjunction + bind + emit。

2. **Build `utils/atom.py` + `utils/rule.py`**
   - input: design doc
   - output: `Atom` dataclass、`Rule` 解析器（读 markdown frontmatter 拿 pattern，body 是说明）
   - acceptance: 10 行 unit-test 跑通；`Rule.from_markdown(path)` 能正确还原 pattern

3. **Build `utils/engine.py` (forward-chaining)**
   - input: atom + rule modules
   - output: `Engine.run(atoms, rules) → (new_atoms, trace)`，trace 是 (rule_id, [parent_atom_ids], derived_atom) tuples
   - acceptance: 3 条合成 rule 在 10 条合成 atom 上 fixpoint 收敛；trace 完整可回放；每条 derived atom 都带 `derived_from` 反向链

4. **Build `scripts/extract_atoms.py` (ingest pipeline)**
   - input: `arcs/all/*/9_summary.md`、`docs/paper_read/*`、`docs/notes/*`、`docs/decisions/*`、`SPECS/*`
   - output: `output/<ts>/wiki/atoms/*.yaml`（按 source 文件分文件）
   - acceptance: 抽出 ≥ 100 个 atoms；至少包含 (i) source_doc 自身的 entity atom、(ii) 文档中提到的其他 arc / path / module、(iii) frontmatter / TL;DR / [NEW]-[UPDATE] 行里的 (subj, pred, obj) triples

5. **Author 10 seed rules + 1 ablation rule (`output/<ts>/wiki/rules/`)**
   - input: extracted atoms
   - output: `output/<ts>/wiki/rules/r001*.md … r011*.md`，每条一份 markdown
   - acceptance: 覆盖 alias / cross-ref / supersede / contradiction-lint / used-by / derived-from-arc 等模式；rule 11 必须刻意挑能 chain 的 pattern

6. **Run engine + measure (`scripts/run_demo.py`)**
   - input: atoms + rules
   - output: `output/<ts>/wiki/derived/*.yaml`、`output/<ts>/run.log`（含 10-rule baseline 数 + 11-rule 增量数）
   - acceptance: 10-rule 跑出 ≥ 50 derived atoms；rule 11 边际 ≥ 5 (或如实记录 < 5 的失败信号)

7. **Spot-check 抽样 (`scripts/spot_check.py`)**
   - input: derived atoms
   - output: `output/<ts>/spot_check.md`（随机 20 条 derived atom 的人工 valid/invalid 判定）
   - acceptance: 写出抽样列表（需要 user 标注，非自动判分）

8. **Build viz HTML (`scripts/viz.py`)**
   - input: atoms + rules + derivations + trace
   - output: `output/<ts>/viz.html`（单页，无 CDN）
   - acceptance: 显示 atoms 表 + rules 表 + 每条 derivation 带 (rule_id → parents) 反向链；warm-paper 视觉契约同 grok-simple

9. **Update `_tmp/report_notes.md`** with strategy / smoke result / load-bearing decisions / final acceptance numbers throughout execution.

## Data Contracts

**Atom YAML** (`atoms/<source_stem>.yaml`)
```yaml
- id: a_0042                       # stable hash of (subj, pred, obj, source)
  subj: arc:260508b
  pred: introduces_doc
  obj: docs/notes/lidar_merge_quality_metric.md
  source: arcs/all/260508b_l2_lidar_merge_metric/9_summary.md
  source_line: 18                  # optional
  derived_from: null               # null = extracted; rule_id = derived
  confidence: extracted            # extracted | derived | conflicted
```

**Rule markdown** (`rules/r###_name.md`)
```markdown
---
id: r003_doc_used_by
when:
  - {subj: ?A, pred: introduces_doc, obj: ?D}
  - {subj: ?B, pred: mentions, obj: ?D}
  - constraint: "?A != ?B"
then:
  - {subj: ?D, pred: used_by_arc, obj: ?B}
---

# r003 · introduces_doc + mentions → used_by_arc

当 arc A 引入 doc D 而 arc B 也提到 D，把 D 标记为"被 B 复用"。
预期 yield：每对 (A, B) 复用相同 doc 时触发一次。
```

**Derivation log** (`derived/*.yaml`, same shape as atoms, with `derived_from: r###` and parent atom ids embedded).

## Smoke Test First

**Smoke (before 任何全量 run)**:
1. 合成 10 条 atoms + 3 条 rules（一条 alias、一条 cross-ref、一条 chain 触发）写在 `scripts/smoke.py` 里
2. 跑 `python scripts/smoke.py`
3. 期望输出：fixpoint 在 ≤ 5 个 iteration 收敛；产出 ≥ 3 derived atoms；其中至少 1 条是 rule chain（即第二条 rule 消费了第一条的 derived atom）

**Real run 的 smoke**:
1. 先在 3 篇 9_summary.md 上跑 `scripts/extract_atoms.py`，肉眼看 atoms 是否合理
2. 选 3 条 seed rules 跑一遍引擎，看 trace 是否可解释
3. 通过后再跑全量

## Risks & Mitigations
- **rules 不组合 → 退化成线性**：rule 11 的 pattern 必须刻意挑能链式触发的（消费 derived atoms）。若边际仍 < 2，如实记录并把 arc 结论改为"抽象证伪 + 提示后续要找别的 collapse"。
- **atom 抽取脏**：先 smoke 看 3 篇，必要时收紧 regex / 加 schema 字段
- **30 篇 source 太少**：如果边际数字噪声大，跑 5 种 rule 加入顺序取中位数
- **DSL 设计漂移**：守住"够用就停"，不引入 negation / aggregation / 算术（这一轮明确 non-goal）
