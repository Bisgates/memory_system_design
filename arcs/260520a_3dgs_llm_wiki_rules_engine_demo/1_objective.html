LLM-Wiki 规则引擎最小可运行原型

用明确规则让 wiki 对 agent 的效益指数增长
I · 目标

在本 arc 内造一个最小可运行的 rule-engine wiki 原型：从 3dgs 现有 markdown sources（arc summaries / SPECS / notes / paper reads / decisions）确定性抽取 atoms，由人手撰写的若干条 pattern → action rules 自动派生新关系（cross-ref / supersede / contradiction-lint 等），用 forward chaining 跑到 fixpoint，并测量第 N+1 条 rule 加入时的边际 derivation 数，验证 "rules × sources" 是否真出现超线性增长。

本 arc 不接管项目实际 wiki — 只是把抽象 down 到可运行代码，让"规则可写、连接可派生、增长可度量"三件事被实证地证明或证伪。

II · 边界

In-scope

  • atom schema（YAML，带 id / subj / pred / obj / source / derived_from provenance 字段）
  • rule DSL（每条 rule 是一份 markdown，frontmatter 写 pattern 字段，body 写说明 + action template）
  • forward-chaining 引擎（≤ 200 行 Python，apply rules to fixpoint）
  • ingest pipeline（deterministic 抽取：title / id / [NEW] [UPDATE] 行 / 路径引用 / 跨 arc 链接 — 不调 LLM）
  • 10 条手写 seed rules + 1 条第 11 ablation rule（用于测边际增益）
  • 单页 viz HTML：atoms 表 + rules 表 + derivation 反向链
  • 跑通 + 输出指标

Non-goals

  • 让 LLM 写 rules（留给后续 arc）
  • 接入项目主 wiki/ 目录（本 arc 的产物全部在 output/<ts>/wiki/ 沙箱里）
  • BM25 / vector search / embedding / qmd
  • 多用户 / web UI / Obsidian plugin
  • conversation-time 增量维护（这是 batch 离线 demo）
  • gpu7 / 长跑 GPU 任务
  • 把 rule DSL 设计成图灵完备（够用就停）

VI · 风险
  • 规则之间不组合（每条 rule 处理独立模式，链式触发不发生）→ 增长退化成线性。检测信号：第 11 条 rule 的边际 derivation 数 < 2。若命中此风险，本 arc 的结论是 "claim 抽象 falsified，需要重新设计"。
  • atom 抽取太脏（regex 在富 markdown 上误抓）→ 大量 false-positive derivations 污染 spot-check 率。Mitigation：先小规模 smoke 检查抽取质量，必要时收紧 schema。
  • 30 个 source 不够看出统计差异 → 单次 run 的边际增益噪声大。Mitigation：跑 5 种 rule 加入顺序，取边际增益的中位数。
