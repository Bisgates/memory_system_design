I · The predicament

为什么不能直接用 Obsidian 双链就完事

手上有一个 Obsidian vault，里面 53 张实验候选 md，8 张 lineage，1 张 anti-pattern catalog，全部 yaml frontmatter + Markdown 正文 + [[双链]]。看起来已经够用——一张卡指向另一张卡，derived_from、competes_with、falsifies，关系都标得清清楚楚。明天来个 agent，让它从 vault 里读出"这次 arc 的 SOTA champion 是谁、它建立在谁之上、谁来挑战它"——它读得出来吗？

读得出来一半。[[双链]] 是字符串，agent 能 grep。但 vault 里没人写过 derives_to——只有 derived_from 的反向；没人写过 competes_with 的对称半边；没人把 anti-pattern catalog 里的 case-example 列表反向接到实验卡上。这些都是 能从已有事实推出来 的事实，可 Obsidian 不推。它只忠实地存。

问题真正的形状
存事实 ≠ 让事实之间互相说话。文件系统给得了第一件事；要第二件，你需要一个能在 读取时 计算的层。Obsidian/Roam/Logseq 都在第一层。

这篇要做的事很简单：把 vault 重新表达成一种格式，让事实之间能互相推、能互相生、能互相校。我会从最小到能跑的内核起步——只有 Card 和 (subj pred obj) 三元组——然后每加一层就只加 一个机制，并交代清楚：前一层撑不住的是什么、加完后能做的新动作是什么、还有什么仍然做不了。最后一层叠完，就是 arc 260521a 实际跑通的设计。

"What's the question behind the question?" — the move that organizes this page

每一层我都会用 arc 260516a 的 SOTA champion 卡 H-R3b-4_c84_kelly_lambda_1.5 走一遍——同一张卡，看它在每一层"被看见"的方式如何变厚。frog tab 里会把这张卡的真实 EDN dump 贴出来。

II · Layer 0

最小可跑内核 — Card + (subj pred obj)

加入的机制
一个 Card 数据结构 + 一个 CardStore 容器；卡的 kvs 里允许有 :subj :pred :obj 三元组。
前一层撑不住
没有"层"——这是地基。
新能做
装数据；按字段查询；按 subj/obj 反向找入度。
还做不了
不能 派生 新事实；不能区分 link 类型；不能 lazy；不能 dedup。

把最少能跑的东西先定下来。一张 Card 就是 (id, type, kvs)，type 暂时全部 'atom'，kvs 是一张开的字典。CardStore 就是一个 dict[id → Card]，加上四个动作：add / get / update / delete，加两个查询：find_links_to(obj) 和 find_links_from(subj)。

这就是一个三元组数据库——RDF 的最简退化、Datomic 的祖先形态。Hamming 的反射在这里出现一次：把 带索引的关系数据 推到极简边界，剩下的就是 (subj, pred, obj)。任何更复杂的 schema 都可以折回这个形状。

H-R3b-4 在这一层长什么样

vault 里那张 SOTA champion 的 markdown，有 30 多个 frontmatter 字段 + 6 种 typed link。Layer 0 把它拆成 58 张卡：1 张 :type "experiment" 根卡（带原始 markdown 作 :body）+ 57 张 :type "atom" 卡，每张表达一条 (subj pred obj) 事实。

(card "a_5189f3d4" :type "atom"
  :subj "exp:H-R3b-4_c84_kelly_lambda_1.5"
  :pred "has_train_nav"
  :obj  3.6981)

等等——has_train_nav 是个 pred 吗？是。在 Layer 0 里 任何字符串都能当 pred，没人管。has_test_nav、has_tag、parent_arc、derived_from、competes_with——全部并排住在一个 namespace 里。这是地基的 freedom，也正是 Layer 1 要解决的混乱。

extreme-case 检查
把 pred 词表推到极限：所有 pred 是同一个串。那 store 退化为一张 (subj, obj) 邻接表，连 type 都看不出来——这是 Obsidian 双链网络的纯粹版本。Layer 0 至少多了 pred 这一维，但 pred 是未约束的。

能做的 trace

装完 53 张 experiment md 之后，store.find_links_to("exp:H-R3b-4_c84_kelly_lambda_1.5") 能告诉你 14 条入度——那些 :obj 指向 champion 的卡。可它没法告诉你：哪些是"基于它做的下游"，哪些是"和它平行竞争"，哪些是"声明它失败"。一切都长得一样。

III · Layer 1

约定 pred 词表 — typed predicate

加入的机制
一份约定俗成的 typed predicate 词表，从 vault 实际用法反推。
前一层撑不住
pred 自由 = 没法按 link 类型 走有向图。
新能做
"谁是 champion 的 derivee"、"谁挑战它"、"谁声明它已被 falsify"——三个不同动作，三条不同 pred。
还做不了
反向边、对称边、传递闭包都得手动写；agent 看不出 derived_from 和 derives_to 是同一关系的两个方向。

这一层不动 cardstore.py 一行代码——它纯是语义层的约束。从 vault 里梳出 6 个"原生" typed pred（vault 写过的双链类型），再扩 3 个从 body 文本里抽出来的：

structural
parent_arc · parent_lineage · builds_on · has_axis
derivation
derived_from · extends · supports
conflict
competes_with · falsifies · contradicts
attribution
reports_to · references_in_case_examples · is_instance_of_anti_pattern

注意——这里有个微妙之处。Layer 1 没有给 store 加上约束："你必须只用这 13 个 pred"。它只是声明了一个词表。任何不在词表里的 pred 依然进得来（vault body 里随手出现的 borrowed_by、same_round_as、inherits_anti_pattern——arc 实际遇到 90 条 warning），它们留在 store 里，等着下一层（Layer 2）的某条规则把它们 canonicalize 到主词表上。

H-R3b-4 在这一层

同一张卡的 58 张拆解里，原本平铺的 link 现在分了类：

typed pred:obj 是谁语义
parent_arcarc:260516a属于哪个 arc
parent_lineagelin:arc_260516a__team_h__sizing属于哪条 sizing 实验线
derived_fromexp:H-R2-2_c84_linear_sizing是 λ=1.0 那版的 amplified 版
builds_onexp:C8.4_top3_no_open3min_bypass用 C8.4 当 trade selector
competes_withexp:B-R8-1_no_open3min_bypass03不同 axis 的 challenger

现在 agent 看到这张卡，能区分清楚——"这是它的上游"、"这是它的对手"。但反向呢？vault 里没人在 H-R2-2 那张卡上写 derives_to: H-R3b-4。没写就没有。如果 agent 问"H-R2-2 被谁继承了？"，Layer 1 答得出来——靠暴力扫描所有卡，看谁的 derived_from 指向 H-R2-2。但这是 O(N) 扫描；想让 agent 顺着 上下游走，需要反向边已经在那里。

"每条 derived_from 都得手动写一遍 derives_to" — 这是 Layer 1 撑不住的 tension
IV · Layer 2

规则即卡片 — rules as cards

加入的机制
一类新的 :type "rule" 卡，带 :when [pattern...] 和 :then [conclusion...]；一个 RuleEngine 跑 forward-chaining fixpoint。
前一层撑不住
反向边、对称边、传递闭包都得人写。
新能做
写一条 r002，全 store 53 条 derived_from 自动 fan 出 53 条 derives_to；规则本身存成卡，能 find_by_type('rule') 查、能 :status "paused" 一键关掉。
还做不了
规则只能 derive 边（新的三元组）；它 derive 不了节点——你没法用 rule 从一张 paper 卡批量生出 3 张新建议卡。

这是真正的拐点。Layer 2 把"事实"和"产生事实的方法"放进同一个 namespace。一张 rule 卡长这样：

(card "rule:r002_derived_from_reverse" :type "rule"
  :body "A derived_from B implies B derives_to A."
  :when (("?a" "derived_from" "?b"))
  :then (("?b" "derives_to" "?a"))
  :status "active")

RuleEngine 的实现刻意单薄——167 行：扫所有 atom + derived，做 pattern unify，把所有满足 :when 的绑定代入 :then，dedup 用 (subj, pred, obj) 作自然键，run_to_fixpoint 反复跑直到没新东西。没有 join 优化、没有 magic set、没有 stratified negation——故意不要。Hamming 反射又来一次：把规则引擎推到极限，就是无聚合、单调 append，并且 fixpoint 保证终止。

arc 260521a 真实跑出来的

11 张 rule card（r001a..g 七张 micro + r002/r003/r004/r005），跑 2 个 iteration 到 fixpoint，99 条 derived 卡。其中：

rule语义fan-out
r001 (a..g)把 body 里非标准 link canonicalize 到主词表16
r002derived_from → derives_to 反向53
r003competes_with 对称闭包20
r004falsifies 传递（A 反 B 反 C ⇒ A inherits_falsification C）0
r005anti-pattern 反向（catalog 引用 → 实验 instance_of）10

r004 那个 0 不是 bug——是 vault 里目前还没出现 falsifies 长链；rule 在那里，等数据到了再点亮。这就是 forward-chaining 的好处：规则不需要"被调用"，它在。

规则作为数据的代价

r002 跑完以后，"r002 这条规则" 自己也在 store 里。可以问：

  • store.find_by_type('rule') → 11 张
  • store.query(lambda c: "reverse" in c.kvs.get("body","").lower()) → 2 张（r001g 和 r002）
  • 把 r002 的 :status 翻成 "paused"，re-run fixpoint → derived 总数 99 → 46，差正好 53。规则的关停是数据操作，不是代码修改。
cross-domain transfer
"规则即数据"是 Lisp 半个世纪的主旋律——defmacro、Datomic 的 :db.fn、Datalog 的 EDB/IDB 平等。Layer 2 把它用到知识库上，得到的不是新概念，而是把这件事真的做了。

tension

r002 fire 出 53 条 derived 三元组，每条都是一行 (?b derives_to ?a) 的小事实。它不能给你 53 张新结构的卡——比如"从一张 paper 卡派生 3 张建议卡（baseline / ablation / extension）"，每张都有自己的 body、自己的 subj/pred/obj、自己的 metadata。规则只 derive 边。要 derive 节点簇，需要更大的工具。

V · Layer 3

宏即卡片 — macros as cards

加入的机制
一类 :type "macro" 卡，带 :params (?source) 和 :body (template-card-1 template-card-2 ...)；一个 MacroEngine 做字面 ?var 替换。
前一层撑不住
规则只 derive 边；要批量生成"新结构的卡"，需要模板展开。
新能做
一张 paper 卡过 m001 macro，立刻 expand 出 3 张 suggestion 卡（baseline / ablation / extension）。模板本身也是卡，find_by_type('macro') 能查到。
还做不了
展开出来的卡是冻结快照——macro fire 那一刻什么样，以后就什么样。store 后续变化不会反映到这些卡里。

Layer 3 的 mechanism 看起来跟 Layer 2 很像——都是"匹配一个模式，产生新东西"。差别在产生物的结构：rule 产生 三元组事实（:type "derived"），macro 产生 整张新卡（任意 :type，任意字段）。

(card "m001_paper_to_experiment_suggestion" :type "macro"
  :name "paper-to-experiment-suggestion"
  :params ("?source-paper")
  :body (
    (:type "suggestion"
     :subj "?source-paper"
     :pred "suggests_experiment"
     :obj  "suggestion_baseline_?source-paper"
     :body "Baseline replication of ?source-paper — re-run...")
    (:type "suggestion" ... :body "Ablation of ?source-paper — knock out...")
    (:type "suggestion" ... :body "Axis extension of ?source-paper — probe...")))

跑 macro_engine.expand("paper-to-experiment-suggestion", {"source-paper": "exp:H-R3b-4_c84_kelly_lambda_1.5"}, ...)，store 多出 3 张 :type "suggestion" 卡：

m_ae8adfd4 → "Baseline replication of exp:H-R3b-4_c84_kelly_lambda_1.5 ..."
m_447765d1 → "Ablation of exp:H-R3b-4_c84_kelly_lambda_1.5 ..."
m_a754873b → "Axis extension of exp:H-R3b-4_c84_kelly_lambda_1.5 ..."

arc 260521a 在 cap1 demo 里跑了 m001 × 3 张源卡（SOTA champion / 被 falsify 的 B-R10-2 / lineage parent H-R2-2），9 张新建议卡。每张都带 :parents [source_card_id, macro_card_id]——provenance 完整保留，可以反查"这张建议是哪个 macro 在哪张源卡上 fire 出来的"。

homoiconicity 落地
macro 的 :body 是 sexp 形式存盘的，跟 atom 卡走同一个 parser；MacroEngine 只做 ?var 字面替换，没有任何 eval。Lisp 把"代码即数据"做了 60 年，这里只用了它最瘦的版本——但已经够。

tension

看一眼 m_ae8adfd4 的 :body："Baseline replication of exp:H-R3b-4_c84_kelly_lambda_1.5"。这串字符是 macro 在 2026-05-20T17:55:31 那一刻替换出来的。明天 H-R3b-4 被 dedup 标 superseded、被 r004 标 inherits_falsification——那张 suggestion 卡不知道。它的 body 是 frozen text，跟 store 当前状态脱钩。

所以下一层要的不是"再做一次展开"，而是"展开出来的东西本身就是一个查询，每次读它都重新评估"。

VI · Layer 4

视图卡 — query as card, materialize on read

加入的机制
一类 :type "view" 卡，带 :query {:filter_pred ... :filter_obj ...}；materialize(view, store) 在读取时跑 filter 返回当前匹配集。
前一层撑不住
macro 展开是冻结快照。
新能做
一张 view 卡说"所有 parent_lineage = lin:sizing 的实验"，store 加一张新 sizing 实验，view 立刻在下次读取时反映出来——不需要重跑任何 macro。
还做不了
view 是整张卡的过滤。如果你想说"卡里某个字段是一个查询、读取时 eval"，view 还做不到——它的颗粒度是卡，不是字段。

view 跟 macro 的关系很有意思——view 是 macro 能产出的一种特殊卡。arc 260521a 的 m002 就专门做这事：

(card "m002_lineage_to_comparison_view" :type "macro"
  :name "lineage-to-comparison-view"
  :params ("?lineage")
  :body (
    (:type "view"
     :name  "view_?lineage_all_candidates"
     :body  "All experiments registered under lineage ?lineage."
     :query (:filter_pred "parent_lineage" :filter_obj "?lineage"))))

m002 在 lin:arc_260516a__team_h__sizing 上 fire 一次，产出 1 张 view 卡。这张卡的 :body 是说明文字，:query 才是 payload。每次 materialize(view, store) 都会扫 store，把所有满足 filter 的卡返回——当前快照，不缓存。

cap5 demo 跑出来

三次 materialize 之间故意改 store：

  1. 初始：14 张 sizing 实验匹配（H-R1-1..H-R3b-4 全套）
  2. 注入一张合成的 (? parent_lineage lin:sizing) atom 卡 → materialize 立刻给 15
  3. 把那张合成卡 delete → materialize 回到 14

view 不缓存的代价是每次都重新扫。3404 张卡的 store，一次 materialize ≈ 几毫秒——可接受。当 store 长到百万级才需要谈索引和增量；现在这个 scale 故意不做。

"view 反映 store 现状，但 view 的边界是整张卡"

tension

m001 fire 出来的 suggestion 卡，body 里写死了 "Baseline replication of exp:H-R3b-4_c84_kelly_lambda_1.5"。这串字符是字段值，不是整张卡。view 救不了——view 的查询只能说"哪些卡进来"，没法说"卡里这个字段的值到读取那一刻才算出来"。

问题：能不能在卡里某个 :body 字段里内嵌一个表达式，读取这张卡时，引擎跑去 evaluate 这个表达式、把它替换成最新值？

VII · Layer 5

字段级延迟引用 — <eval> at retrieve

加入的机制
允许 :body 字段里内嵌 <eval>expr</eval>；store.resolve_lazy(card) 在读取时把 expr 跑出结果替换回去。
前一层撑不住
view 的颗粒度是卡，不是字段。
新能做
一张卡里写 <eval>count-links-to exp:H-R3b-4_c84_kelly_lambda_1.5</eval>，读取时得到当前入度 14；明天来了新引用、读取自动变 15。latest-of 同理，取另一张卡的当前 body 内嵌进来。
还做不了
表达式词表是枚举的——latest-of、count-links-to 两个动词写在 cardstore.py 的 resolve_lazy 里。一个真正的 s-expr evaluator 不在 kernel 范围内（诚实地说）。

这一层不复杂，但位置关键。它把"求值时机"从写入时彻底移到读取时——而且颗粒度细到字段值内嵌的一段串。看看 cap2 demo 的输入：

view_card.body =
  "Latest SOTA snapshot:
   champion body excerpt → <eval>latest-of exp:H-R3b-4_c84_kelly_lambda_1.5</eval>
   inbound link count for champion → <eval>count-links-to exp:H-R3b-4_c84_kelly_lambda_1.5</eval>
   inbound link count for parent (H-R2-2) → <eval>count-links-to exp:H-R2-2_c84_linear_sizing</eval>"

跑 store.resolve_lazy(view_card)，输出：

champion body excerpt → ---
  nav: 1
  type: experiment
  ...（H-R3b-4 完整 markdown 内嵌进来）
inbound link count for champion → 14
inbound link count for parent (H-R2-2) → 11

有意思的是实现：resolve_lazy 一共 20 行——一个正则匹 <eval>(.*?)</eval>，按第一个 token 分派到两个 hardcoded handler。Hamming reflex 第三次：把这件事压到最薄——既然只有两个 verb 在用，先写两个；明天需要第三个，加 7 行；什么时候 verb 多到代码丑了，再上 s-expr evaluator。

为什么不现在就写 evaluator
YAGNI + Hamming：把 evaluator 现在写出来，得花一周；用着两个 verb 跑了三个月才知道实际需要什么形状。把基础设施推迟到第二次出现需求时再建——这是工程而非学术。

tension

跑了几天以后，store 长到 3404 张卡。某个 agent 试图加一张新的 hypothesis claim 卡——可它跟已有的 H-R3b-4 hypothesis 卡相似度 0.969。是新事实？是 paraphrase？是 patch？kernel 没有规则处理这个；写死哪个版本胜不灵活；让 agent 每次都问 han 又太吵。

需要一个机制：让每张可能产生冲突的卡，在被加进 store 之前，自带它的冲突处理方案。

VIII · Layer 6

冲突协议作为数据 — dedup restart

加入的机制
卡上加 :on-dedup-conflict (action-1 action-2 ...)；新卡入库前先 find_near_dupes，命中就执行 head action。
前一层撑不住
store 增长不可逆，没有冲突协议会累积污染。
新能做
同一张高相似度新卡，三个不同的 :on-dedup-conflict 头部 → 三条不同的协议路径（keep-both / merge-prefer-newer / supersede），dedup engine 不需要 hardcode 冲突类型。
还做不了
这里到顶了——arc 260521a 的全部 6 capability 都覆盖到这一层。后面是 forward look。

把"冲突怎么处理"这件事，从引擎里的硬代码挪到卡片自己的字段。dedup.py 144 行，核心动作就两个：_action_keep_both（双向加 :see-also）和 _action_supersede（旧卡翻 status: "superseded"，记 :superseded-by，新卡记 :supersedes [...]）。引擎不知道"应该 keep 还是 supersede"——卡自己说。

cap4 demo 实测

构造一张跟 H-R3b-4 的 has_section_hypothesis atom 相似度 0.8358 的变体（修了 5-10% 文字），跑三次入库，每次只换 :on-dedup-conflict 列表的头：

case:on-dedup-conflict headaction 触发store 状态变化
1keep-bothkeep-both双方互加 :see-also，原卡 status 不变
2merge-prefer-newermerge-prefer-newer原卡 status: "superseded"，:superseded-by = 新卡
3supersedesupersede同 case 2（这俩同义）

三个 action 都 fire 了。引擎只有 144 行；要新加一种 action（譬如 "branch-and-mark-as-fork"），只要写 _action_branch 然后在 resolve_conflict 的分派里加一行——卡端不变。

"冲突协议不是代码——是数据。每张卡自己说"

到这里 kernel 就完整了

把六层叠起来，arc 260521a 的全部 6 capability 都能跑出来：

  • Layer 2 (rules-as-cards) → cap3：rule 自己是卡，查得到、能 paused

IX · Forward look

Layer 7+ — 没做但显然该做

状态
这一节全是 forward look。设计上有位置，arc 260521a 没实现。
下文每一条都未在 arc 260521a 内 implement / verify。列在这里是为了诚实地标出 kernel 的当前边界。

L7 · consolidation worker（仿 sleep replay）

store 长到 N 张卡之后，需要一个夜间 worker 跑：合并高相似度对（夜间打 batch 而不是 ingest 时打）、跑 utility prune（按 used_count + recency + link_count - age 评分淘汰 long tail）、检查 falsifies-cluster 有没有新的 cycle。当前 kernel 是append-only，没有这层。

L8 · 三层 index（symbolic / vector / graph）

Layer 0 只有 by-id 字典 + 反向 obj 扫描。检索要不退化，至少需要三种 index：

  • symbolic — 按 pred 倒排（agent 问"所有 falsifies 链"，直接走 pred index）
  • vector — body 文本的 embedding，做近义检索（dedup.py 现在用 SequenceMatcher，够 demo 不够规模）
  • graph — derived_from / builds_on / parent_lineage 的有向图索引，跑可达性

L9 · 多 agent namespace

当前 store 是 single-tenant。3dgs 项目、quant 项目、life 项目、TARS-meta 各自的卡片如果都进来，需要 namespace 隔离 + 选择性 cross-link（譬如 "TARS 的人格契约卡可以被 quant agent 引用"）。

L10 · 多 agent 并发 write 的 transaction model

当前 RuleEngine 单线程跑 fixpoint，没有并发问题。两个 agent 同时往 store 写——尤其各自带 dedup restart——需要 transaction / optimistic-lock 类的机制。这是把数据库该补的洞补上，不是 wiki 的新概念。

L11 · 自计算字段的真 s-expr evaluator

cap6 demo 的 :confidence (compute (- supports contradicts) / (max supports 1)) 字段，现在的实现是结构匹配——只识别这个 canonical 表达式形状的 token sequence，不是真的 eval。要做 self-computing fields 普遍化，需要把 Layer 5 的 <eval> 词表换成真的 s-expr evaluator + 安全沙箱。这是已经知道形状、只是工程量大。

之前那篇 (arc_260521a_wikify_alpha_second_vault_summary.html) 是按phase 组织——predicament → 4 properties → 5-component kernel → typed vocabulary → 6 capabilities → 工程权衡。它讲的是这周做了什么。

meta-reflection · pull when details fade

the layered move, distilled

每一层都把差异化往下推一格——L0 全是 atom；L1 给 atom 装 typed pred；L2 给 store 加 rule 卡；L3 加 macro 卡；L4 加 view 卡；L5 给字段值加 lazy；L6 给冲突路径加数据驱动。引擎不长肉；卡片接管。

这是 Lisp 的传统、Datomic 的传统、SQLite 的传统——把区分放在数据里，不放在代码里。代码做的事永远是"对一切卡都做同一件事"；卡说自己是什么。

下一次设计任何 agent LTM，可以问的第一个问题不再是"我要存什么"——而是"哪些区分我要让卡片自己承担"。

def resolve_lazy(self, card: Card) -> Card:
    resolved = copy.deepcopy(card)
    body = resolved.kvs.get("body", "")
    if not isinstance(body, str):
        return resolved

    def replacer(m):
        expr = m.group(1).strip()
        parts = expr.split()
        if parts[0] == "latest-of" and len(parts) == 2:
            ref = self.get(parts[1])
            if ref:
                return str(ref.kvs.get("body", f"[no body on {parts[1]}]"))
            return f"[not found: {parts[1]}]"
        if parts[0] == "count-links-to" and len(parts) == 2:
            return str(len(self.find_links_to(parts[1])))
        return m.group(0)  # unknown expr, leave as-is

    resolved.kvs["body"] = re.sub(r"<eval>(.*?)</eval>", replacer, body)
    return resolved
