Peter Norvig × 一份设计稿

如果 LLM-Wiki 是一个 Lisp 程序

1958 年，McCarthy 写下了 eval。1945 年，Bush 想要 Memex。中间一直缺的，是一台能理解符号含义的解释器。
Peter Norvig · 风格仿写 · 2026 年 5 月
I · 提问

我们到底在做什么？

先把那篇 markdown 提出的主张写成一句话：让 LLM 增量地建造一份持久的、互相链接的知识仓库，所有跨页引用、矛盾标注、综述更新都由它代劳，而你只负责选材料、问问题。读完之后我想问的第一个问题，不是"怎么实现"，而是"这是一种什么形状的程序？"

顺手就能想到的答案，是把它写成一坨 Python 脚本：读 markdown，调 OpenAI API，写文件，重复。这能跑起来，能 demo，能发推。但请允许我直接说出我的判断：这个写法没有捕捉到问题真正的形状。它把一个本质上是符号系统的增量演化问题，写成了文本批处理问题。这两件事在表面上长得很像，但你写第一千行代码的时候它们会分道扬镳。

三种读法 · 同一份 markdown

(a) RAG 读法：把 markdown 看作语料，每次提问时检索 chunk，拼接，回答。知识不积累，每次重头来。
(b) 文本批处理读法：每次 ingest 就跑一遍脚本，更新一些文件。能积累，但更新逻辑散落在脚本里，无法自描述、无法自修改。
(c) 符号环境读法：把整个 wiki 看作一个解释器的全局环境，page 是绑定，link 是符号引用，schema 是元解释规则。LLM 是 eval。

这三种读法的差别，不是工程实现的差别，是抽象层次的差别。markdown 那篇文章本身停在了 (b)：它给出了三层架构（raw / wiki / schema），给出了三种操作（ingest / query / lint），把这些当成"模式"来描述。但它没有给这个模式一个名字。我想说的是：这个模式有名字，它叫 Lisp。

所以我们要问的真正问题是：什么样的编程范式天然就是"增量维护一个一致的、可自描述的符号系统"？这个问题的答案早就有了，只是答的人是 1958 年的 John McCarthy。

II · 同构

Wiki 即 Lisp 环境

让我把对应关系直接画出来。这不是比喻，是同构——给两边一个明确的映射函数，每一项都能拎出去单独验证。

LLM-Wiki 概念Lisp 对应物它们共享的性质
raw sourcequoted form  '(...)不被求值；只读；是事实而非主张
wiki pagebinding  (define name expr)命名 + 可被引用 + 可被更新
[[wikilink]]symbol reference引用按名解析；允许悬空（forward ref）
index.mdglobal environment名字到内容的查找表
log.mdevaluation trace按时间顺序的 read-eval 记录
CLAUDE.md / schemaread/eval 规则 + macro 定义告诉解释器怎么读、怎么求值、怎么扩展
LLM agenteval把表达式解释成更新后的环境
ingest(eval (read source) env)读 → 求值 → 副作用作用于 env
query(apply LLM (lookup env q))从 env 查相关绑定，组合，回答
lintenvironment consistency check扫描所有绑定找出矛盾

我列这张表，目的不是炫耀类比。类比谁都会做。我想说的是：每一行的"共享性质"都是可以决定设计的。"raw source 是 quoted form"不只是好听，它告诉你：raw 目录里的文件应该是只读的，LLM 不能写它，git diff 应该总是空的——这是一条工程纪律，是同构带来的真约束。

worked example · 一页 wiki 看成一段 Scheme

取 markdown 里那个 Tolkien Gateway 的例子。设想你正在为一本小说做 wiki。读完第 3 章后，wiki 里有这三个文件：

; entity/Frodo.md
(define-entity Frodo
  (kind  hobbit)
  (from  Shire)
  (mentions Bilbo Gandalf)
  (claims (carries The-Ring) (chapter 1))
  (sources "chapter-1.md" "chapter-3.md"))

; concept/The-Ring.md
(define-concept The-Ring
  (created-by Sauron)
  (related (entity Frodo) (entity Bilbo))
  (sources "chapter-1.md"))

; index.md
(catalog
  (entities  Frodo Bilbo Gandalf Sauron)
  (concepts  The-Ring Shire))

这当然不是真的 markdown——但等一下，markdown 几乎已经是这个东西了。Frontmatter 是属性列表，[[link]] 是符号引用，标题层级是嵌套。markdown 的语法是 S-expression 套了一层皮。这就是为什么 LLM 写 markdown 写得这么舒服：它是带语法糖的 Lisp。

现在第 4 章来了，里面写到 Frodo 在 Bree 遇见 Strider。ingest 这件事，在符号环境读法下，就是这样一段计算：

(ingest! "chapter-4.md")
  ↓ ; read-extract
'((Frodo meets Strider at Bree)
  (Strider identity-is Aragorn))
  ↓ ; eval — apply to env
(update! Frodo (mentions+ Strider) (sources+ "ch-4.md"))
(define-entity Strider (alias-of Aragorn) (sources "ch-4.md"))
(define-entity Aragorn (introduced-as Strider) (sources "ch-4.md"))
(define-place  Bree    (sources "ch-4.md"))
(log! "[2026-05-20] ingest | ch-4 | +4 entities, +1 alias")

注意一件事：ingest 的结果本身又是一段 Lisp 形式。LLM 不是在改文本，它在生成一段对环境的修改程序。这段程序是可读的、可审计的、可回滚的（git）、可重放的（log）。这就是 homoiconicity 在做事——代码是数据，所以 LLM 写出来的"修改"和被修改的"知识"用同一种符号系统表达。

程序是数据，数据是程序。
同样一句话，写于 1960 年，今天读起来像是为 LLM 准备的。 McCarthy · Recursive Functions of Symbolic Expressions · 1960

顺便：那个 schema 文件（CLAUDE.md / AGENTS.md）放在这个映射里是什么？它是 read/eval 规则的元描述。它告诉 LLM："看到一个人名就 define-entity，看到一个地名就 define-place，看到 X mentions Y 就更新 Y 的 mentions 字段"。这些规则本身是 wiki 的一页——它和别的页同形式、同语法、同语义。schema 改 schema 这件事，在 Lisp 里有个名字：宏。

III · 50 行

把契约写成可运行的草图

我有一个习惯：判断一个想法是否清楚，就看能不能在 50 行以内把它写完。我以前写过一个 Scheme 解释器，叫 lispy，连同测试一共 117 行；那次的收获是，当你能把一件事压到 50 行，你才真正理解了它。多余的复杂度全部是没想清楚的产物。

所以我们试一下。把 LLM-Wiki 的全部契约——三层结构、三种操作、增量演化——压到一段 Scheme，看看剩下的核心是什么。

;; ============================================================
;; llm-wiki.scm — 把 markdown 那篇文章压到能编译的形状
;; LLM 在这里是一个外部 oracle，签名是 (LLM prompt context) → form
;; ============================================================

(define raw   '())        ; quoted forms, 只读
(define wiki  '())        ; mutable env, LLM 写, 你读
(define log   '())        ; append-only trace
(define schema (load "CLAUDE.md"))   ; read/eval 规则

(define (ingest! src)
  (let* ((forms   (LLM 'extract  (cons src schema)))
         (touches (LLM 'integrate (list forms wiki schema))))
    (for-each apply-edit! touches)
    (log! 'ingest src (length touches))))

(define (query q)
  (let* ((relevant (LLM 'find      (list q (index wiki))))
         (pages    (map resolve relevant))
         (answer   (LLM 'synthesize (list q pages schema))))
    (log! 'query q (length pages))
    answer))                          ; 你可以把答案再 ingest! 回去

(define (lint!)
  (let ((issues (LLM 'audit (list wiki schema))))
    (log! 'lint (length issues))
    issues))                          ; 返回，由你决定改不改

(define (repl)
  (display "> ")
  (let ((u (read)))
    (cond ((source? u)   (ingest! u))
          ((question? u) (display (query u)))
          ((command? u)  (apply-meta u))         ; 改 schema
          (else           (display (query u)))))
  (repl))

26 行，把那篇 markdown 的全部主张写完了。注意没出现的东西：embedding、向量库、检索框架、chunk 大小、prompt 模板字符串。它们都能有，但都不在契约里。契约里只有 read / eval / log / repl 和一个名叫 LLM 的外部 oracle。剩下都是工程化的选择。

这段代码里值得停下来看的地方有三个：

观察一 · ingest 返回的是一段程序

touches 不是文本，是一份"对 wiki 的修改操作清单"。每一条都是一个 apply-edit! 可以执行的 form。这就是为什么 git 能记住每一次 ingest 改了什么——你提交的不是一个 LLM 输出，是一段由 LLM 生成、对环境的明确修改程序。

观察二 · query 的结果可以再 ingest

你问的问题、得到的答案，是一份新的 form。它和源材料同形式，所以可以走回 ingest!。markdown 那篇说"good answers can be filed back into the wiki"——那是一句正确但散漫的话；在这里它变成了类型签名：query → form，ingest!: form → unit，组合是合法的。

观察三 · repl 即 dev loop

你和 LLM 的对话就是 REPL。每一条输入要么是源材料（quoted form），要么是问题，要么是元命令（改 schema）。没有"我先写程序、再跑程序"这一步。Lisp 程序员理解这是什么——image-based、live-coded、不区分写和跑。这是 wiki 该有的工作模式，而不是"我先训练好一个系统、再使用它"。

worked example · 一次完整的 ingest，按 form 展开

用前面那段 Lord of the Rings 的小宇宙跑一次。输入：第 4 章的 markdown，里面有 "Frodo arrived at Bree and met a ranger called Strider"。计算过程：

> (ingest! "raw/ch-4.md")

; step 1 · LLM 'extract  →  返回一段 quoted form
'((meet Frodo Strider (at Bree))
  (alias Strider Aragorn))

; step 2 · LLM 'integrate  →  返回一组 edits，引用现有 env
(update-entity Frodo   (mentions+ Strider) (sources+ "ch-4"))
(create-entity Strider (alias-of Aragorn)  (sources "ch-4"))
(create-entity Aragorn (intro-as Strider)   (sources "ch-4"))
(create-place  Bree    (sources "ch-4"))

; step 3 · apply-edit! 逐条改 env，git 看到 4 个文件被改
; step 4 · log! 追加一行
"## [2026-05-20] ingest | ch-4.md | +3 entities +1 place"

这里的关键不是 LLM 多聪明，是每一步的中间产物都是 S-expression。你可以 print 它，可以 diff 它，可以拒绝它（"step 2 第三行错了，Aragorn 在第 5 章才正式登场，不要现在创建"），可以重放它。它不是黑盒的"AI 在写文件"，是一段你能审计的小程序。

IV · 设计稿

那么，具体怎么搭？

同构是设计的地图。把同构当真，下面这份草图几乎是写出来的，不是设计出来的。

directory · 三层映射到三个目录

project/ ├── raw/ # quoted forms · 只读 · git ignored 的是大文件，markdown 入库 │ ├── ch-1.md │ ├── ch-4.md │ └── assets/ # 图片 · 由 web clipper 下载 ├── wiki/ # env · LLM 写 · 你读 · git 追踪每次 ingest │ ├── index.md # catalog · 入口环境 │ ├── log.md # trace · append-only │ ├── entity/ │ │ ├── Frodo.md │ │ └── Aragorn.md │ ├── concept/ │ │ └── The-Ring.md │ ├── place/ │ │ └── Bree.md │ └── answer/ # query 答案归档 · 也是 page │ └── 2026-05-20--who-is-strider.md ├── CLAUDE.md # schema · read/eval 规则 · 等同 .emacs 或 init.lisp └── .git/ # 版本即历史快照 · 不需要单独的撤销机制

没有 vectors/，没有 chunks/，没有 embeddings.faiss。在初期一律不要。索引就是 index.md 文件，符号查找就是 grep。这是 Lisp 信念的应用：能用列表搜索的，就不要建哈希表；能用文件名查找的，就不要建数据库。等到 wiki 真的长到 grep 不够用了——可能在 1000+ 页的时候——再上 qmd 这类 BM25 + 向量混合搜索。不要提前一秒。

schema · 把 CLAUDE.md 写成宏定义集

markdown 那篇说"schema is the key configuration file"，但没给形式。我给一个：把 schema 看作 read 规则 + eval 规则 + 一组宏。每条规则形如"当看到 X，做 Y"——也就是模式 → 重写规则，这是 Lisp 宏的本质。

; CLAUDE.md  —— 用人类语言写，但每段都对应一个 macro

## read 规则
1. raw/ 下的文件是 quoted——你可以读，不可以改。
2. wiki/ 下每个 .md 是一个 binding；文件名是符号名。
3. [[X]] 是符号引用；解析时去 wiki/ 全局环境查找。

## eval 规则 (ingest 钩子)
- 看到一个新人名 → define-entity，建 entity/<Name>.md
- 看到 X mentions Y → 在 X 和 Y 的 mentions 字段互相 +1
- 看到 "X is also called Y" → 建 alias 关系，不建新 entity
- 看到与现有 claim 冲突 → 不要静默改写；在两边各加 contradiction 标记

## eval 规则 (query 钩子)
- 先读 index.md 找候选 page
- 每个候选展开成 page + 它的 [[link]] 邻居（深度 1）
- 引用必须带 (source ch-N) 后缀，否则 reject 自己

## meta 规则
- 你可以提议修改本文件。修改必须显式：先 propose，再 apply。
- 修改后立即把 schema 自身的 history 写一行到 log.md。

这看起来像散文，但每一条都能机械地翻译成一个 (pattern → action)。等到你写了几个月、对自己的领域积累了独特的规则，CLAUDE.md 会从十几行长到几百行——而它仍然是 wiki 里的一个 page，被 git 追踪，被 lint 扫描。schema 即数据，数据即 schema。这是 Lisp 派 30 年来一直坚持的同一个论点。

operations · 四个动词，仅此而已

动词类型签名实现要点
ingest! source → unit (env mutated) 两步 LLM 调用：extract 拿 forms，integrate 拿 edits。edits 必须是显式 form，不能是自由文本。每条 edit 落到一个 file write，逐条做，逐条 git stage。
query question → form (可再 ingest) 三步：find candidates（看 index.md）→ resolve（读 candidate 的 page）→ synthesize（产生答案）。答案是 markdown，归档到 wiki/answer/<date>--<slug>.md。
lint! unit → list of issue 扫四种东西：orphan page、stale claim、缺失链接、待补 source。每个 issue 是一份 form，你决定 apply 还是 ignore。
amend-schema! proposal → unit 显式的元命令。propose 阶段 LLM 写出一份 diff；apply 之前你确认。改完 log 一行——这是元解释器在自我修改。

四个动词，外加 git。没有 admin 面板，没有 web UI，没有数据库 schema 迁移工具——你不需要。Lisp 的 image-based 哲学在这里复活：整个项目就是一个目录，关掉电脑明天打开，状态在那里。Obsidian 是个 viewer，可有可无；真要做也只是给 wiki/ 加一个图形渲染层。

V · 杠杆

推一推参数，看它退化成什么

Hamming 有个习惯：拿一个方法，把参数推到 0 或 ∞，看它退化成什么。极限的形状揭示一般情形的结构。这里也试一下。

极限 → 0 · wiki 为空

所有内容都还在 raw/。env 是空环境。这时 query 退化成 RAG——LLM 临时把 raw 当语料检索。这正是市面上大部分系统的常态：它们停在 wiki-size = 0 的边界条件上，永远不离开。LLM-Wiki 的全部价值在这个变量的动力学上——它把状态从 0 推走、并保持推走。

极限 → ∞ · wiki 比 raw 大

每个事实在 wiki 都有自己的页面，schema 里每条规则都演化成几十个具体绑定。这时 raw 几乎可以归档不读——所有的"知识"已经在 wiki/ 里被消化为符号了。这是 Memex 的极限态，Bush 1945 想的就是这个。让人在十年里读了 5000 篇文章后，仍然不丢失对这 5000 篇之间联系的把握。

动力学的两端都告诉我们：这个系统的本质参数不是 page 数、不是 token 数，是 wiki 的"自包含度"——能不再回头读 raw 而独立回答多少问题。Lisp 程序员管这个叫 environment closure。设计的全部目标，就是让闭包越长越紧。

cross-domain · 这把刀以前砍过什么

"增量维护一个可自描述的符号系统"这个形状，不是 LLM-Wiki 的发明。它出现过至少三次：

  • Emacs / Org-mode。一个 org 文件既是数据（待办、笔记、链接）又是代码（Babel block 可执行）。C-x C-e 把光标处的表达式求值——同一个 buffer 里既是编辑器又是解释器。
  • Mathematica notebook。每个 cell 是 S-expression，notebook 自己就是 expression。整个系统是一个可保存的 image。
  • Smalltalk 镜像。没有"源代码"和"运行时"的分别。所有 object 都活在 image 里，包括开发工具自身。改了立即生效，关闭电脑保存全部状态。

这三件事，加上 Lisp 的 image-based REPL，是同一个隐含设计的四个化身。LLM-Wiki 是第五个，区别只在于：前面四个的 eval 是确定性的语义函数，这里的 eval 是一个理解自然语言的概率函数。LLM 不是新东西，它是一个长得不一样的 eval。

AI programming has been Lisp-shaped since 1958.
The LLM didn't change that. It just gave us an eval finally smart enough to deserve the contract. Norvig · PAIP · 1992（精神改写）
VI · 尾声

抽掉细节之后剩下什么

如果你把这篇全部忘掉，只留一句话，那句话是：当一个问题的形状是"增量维护一个一致的、可自描述的符号系统"，你已经站在 Lisp 的主场上，无论你写不写括号。

Bush 在 1945 年描述了 Memex，但他没有 eval。McCarthy 在 1958 年给了 eval，但没有人能写出足以解释自然语言的求值规则。中间 80 年，所有"个人知识库"的尝试都卡在同一个地方——bookkeeping 是 Lisp-shaped 的，而人不愿意做 Lisp 的解释器。维护跨页引用、保持综述同步、标注矛盾、回滚错误结论——这些事在结构上属于 eval，但执行起来需要一个又懂语义、又愿意逐字检查的劳力。

LLM 是那个劳力。它不是新的概念，它是 1958 年起就等在那里的 eval 的实现。markdown 那篇文章描述的所有"操作"——ingest 写 10 个文件、query 走链接图、lint 找矛盾——在 Lisp 派的语汇里都是同一个动作：解释器在维护它的环境。

能不能用 LISP 的逻辑来构建？我的答案是：你必须用 Lisp 的逻辑来构建。表面上写不写括号、用不用 Scheme、跑不跑 SBCL，这些都是表层选择——markdown 完全可以是你的语法糖，Python 完全可以是你的宿主语言。但背后的设计模型必须是 read/eval/print 加上一个会演化的环境，否则你会写出一个不积累的系统，或者一个积累但不一致的系统，或者一个一致但你无法审计的系统。三种失败已经发生过几千次了。

所以最后那条建议很短：在你写下第一行代码之前，先把 wiki 想象成一段 Scheme 程序。每页是 binding，每个 link 是符号，CLAUDE.md 是 read 规则，LLM 是 eval。你写下的工程实现，应该是这段想象中程序的一个保真投影。这样你既得到 markdown 的可读性、又得到 Lisp 的可组合性、还得到了 LLM 这个迟到了 70 年的 eval 实现。

剩下的事情，按 Alan Perlis 的话办：

Within a computer natural language is unnatural. Alan Perlis · Epigrams in Programming · 1982 · #29

但反过来也成立：在一个被 LLM 求值的系统里，自然语言是合法的 S-expression。这两句话第一次同时为真，是 2024 年前后的某个春天。我们正好赶上了。
