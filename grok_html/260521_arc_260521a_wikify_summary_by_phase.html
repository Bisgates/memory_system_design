The predicament

The alpha_second_v1 auto_research_experiment vault is already a high-discipline Obsidian directory: every candidate paper has YAML frontmatter, six declared typed-link predicates (parent_arc, parent_lineage, derived_from, competes_with, falsifies, reports_to), and seven layered tag axes (#axis/sizing, #status/falsified, #leak/clean, …). If you read it as a human, it works. So why touch it?

Because Obsidian is a reading surface. It renders links; it does not compute on them. An agent that wants to derive a new card, compose a query, pause a piece of inference, or materialize a lineage view on the fly cannot do any of that against a directory of markdown. The vault's typed links are real edges, but they live in body bullets that look like prose. The tags are real axes, but they live in YAML lists. To compute, an agent has to first parse — every time, for every question.

The 260521a arc replaces that with a flat (card …) s-expression store where every datum — atoms, rules, macros, derived facts, materialized views — lives in the same :id namespace and is queryable through the same API. The Obsidian vault stays put; this is a parallel layer for the agent side.

The bet: if "everything is a card" (data, rules, macros, derived facts, views all sharing one schema and one query API), the next agent that wants to extend this knowledge base does not need to write a new parser or a new index. It just adds another (card …).

A second-order claim, less obvious but more important: computational relations are first-class. The vault already has read-time links (Obsidian double-brackets). What it lacked is the ability to say things like "everywhere I wrote borrowed_by, I also mean its canonical form" or "this view should reflect whatever is in the store right now, not what was there when I authored the view." Those statements are themselves data; in 260521a, they live in the same store as the candidates they describe.

The vault is not deprecated. The Obsidian directory still serves humans; the EDN store serves agents. They sit side by side, sourced from the same markdown, kept in sync by a one-step ingest. If the structural parser breaks because someone introduces a new H2 label or a new typed-link verb, the failure is loud (warnings in phase2_ingest.log) and recoverable (canonicalize via a new r001-* micro-rule).

The four properties an agent-readable store needs

Before the decision tree, the rubric. There are dozens of ways to wikify a directory of markdown; not all of them give an agent something it can actually compute on. We held the design to four properties:

P1Single-API uniformity

The agent must not have to know in advance which kind of card it is reading. store.get(id) works for an experiment, a rule, a macro, a view, a derived fact. find_by_type takes a type as data. If the agent learns one verb it can interrogate everything.

P2Provenance survives the round trip

Every derived card carries :derived_from (which rule or macro produced it) plus :parents (which atoms were the inputs). Delete a source atom; the derived cards that pointed at it become inspectable orphans. Pause a rule; we know exactly which derived cards belong to it.

P3Idempotent reruns

Phase 2 ingest is deterministic in ID space. Phase 3 fixpoint dedups by (subj, pred, obj). Phase 4 demo writes only into output/<run-id>/. The whole pipeline can be re-run from scratch and produces the same on-disk state (up to timestamps).

P4Computational fields are data, not code

:confidence (compute …), :body "<eval>latest-of X</eval>", :query (:filter_pred … :filter_obj …). The agent can read these without executing them, or ask the store to resolve_lazy / materialize on demand. There is no hidden Python that must run to make a card meaningful.

P1 and P2 are easy to claim and hard to keep — splitting a "rules" table off into its own schema feels natural, and every time we did it on paper we ended up violating P1. The cure was to refuse the split: rules go in wiki/cards/rules/ as a filesystem convenience, but the schema is the same and the loader is the same.

P4 is the most distinctive property and the one most easily mis-implemented. The naive version is to evaluate the expression at write time and cache the result. We resisted that. The whole point of "self-computing fields" is that the field re-evaluates when the surrounding data changes — exactly like a spreadsheet cell, not like a build-time macro.

The five-component kernel

The whole system fits in 1479 Python LOC including tests. Each module has one job and is independently testable.

cardstore273 LOC · 6 tests pass

The dataclass + the EDN reader/writer. Card(id, type, kvs). store.find_by_type('rule'), store.get(id), store.outbound(id), full roundtrip. The schema does not know about rules or macros; it knows about cards.

macro103 LOC · 3 tests pass

MacroEngine.register(card), expand(name, bindings). ?var substitution in the body, :parents chain preserved so every derived card knows which macro produced it.

rules167 LOC · 2 tests pass

Pattern-matching forward chainer. :when is a list of triples with ?-prefixed variables; :then is the conclusion. run_to_fixpoint iterates until a pass adds zero new triples. Dedup is by canonical (subj, pred, obj).

view84 LOC · 2 tests pass

A view card stores a :query (filter by type / pred / obj / tag). store.materialize(view_id) evaluates it at read time — there is no cache. Adjacent helper: resolve_lazy(body) swaps <eval>latest-of X</eval> for the current body of card X.

dedup144 LOC · 2 tests pass

Text + structural similarity (Jaccard on body tokens × overlap on kvs keys), the restart protocol (keep-both / merge-prefer-newer / supersede), and the see-also wiring. Used when an external pipeline writes a card that looks 80%+ like an existing one.

smoke_test265 LOC · end-to-end PASS

Not a module — a Phase 1 ship gate. 8 atoms + 5 derived + 1 rule + 1 macro + 1 view round-trip through EDN, store back from disk, fire the rule, expand the macro, materialize the view. 15/15 unit tests + 1 end-to-end. That gate is what let Phase 2 start.

How a card travels through the system

The flow is one-way: vault md → ingest → atoms on disk → rules fire → derived atoms on disk → macros dispatch on demand → derived suggestion / view cards on disk → viz renders the union. Every stage is idempotent; rerunning Phase 2 on an unchanged vault produces byte-for-byte identical EDN (modulo the :ingested_at timestamp).

Read it as a pipeline from left to right:

  1. Source — a markdown file in auto_research_experiment/experiments/ (or lineages/, or ANTI_PATTERN_CATALOG.md, …).
  2. Structural parser — ingest_vault.py reads frontmatter via PyYAML, walks H2 sections via regex, extracts double-link references with a paired-bracket scanner. Output: a stream of (subj, pred, obj) triples plus one source card per file.
  3. Atom EDN — each triple becomes (card "a_<hash8>" :type "atom" :subj … :pred … :obj … :source … :ingested_at …). The hash is deterministic. The file wiki/cards/atoms/<source-stem>.edn holds the source card and all its atoms.
  4. Rule fixpoint — run_rules.py loads the atom store + the 11 rule cards from disk, calls RuleEngine.run_to_fixpoint, and writes the resulting derived cards to wiki/cards/derived/<rule-id>.edn (one file per rule, grouping its fan-out).
  5. Macro dispatch — same script reads the 2 macro cards and runs the demo expansions. Macro outputs land in wiki/cards/derived/m001_*.edn and wiki/cards/derived/m002_*.edn.
  6. Demo capability run — demo_capabilities.py loads the union and exercises all six capabilities; each cap writes its own subdirectory under output/<timestamp>_demo_run/ with stdout.log + a JSON trace.
  7. Viz build — build_viz.py walks the union, computes a Fruchterman-Reingold layout in pure Python (no networkx), and emits a single viz.html.

Every script is a Python file with a main() and a --run-dir flag for idempotent reruns. No state lives in environment variables; the run-dir is the only mutable thing.

The six capabilities — what each one is actually for

1 · Macro derivation — cards that copy themselves

The macro m001 paper-to-experiment-suggestion takes one experiment card and emits three: a baseline-replication, an ablation, and an axis-extension. Each suggestion's :parents field points back to both the source card and the macro card, so provenance is intact. This is the "I have a candidate, give me three follow-ups" reflex pattern that an agent runs hundreds of times.

The macro is not magic; it is a card holding a body of templates. MacroEngine.expand walks the templates and does ?var substitution, then writes one card per template into the store. The agent can read the macro card itself (store.get('m001_paper_to_experiment_suggestion')) and see exactly what it is going to produce before running it. That's a property the original "macro = Python function decorated with @macro" design would have lost.

2 · Lazy reference — read-time evaluation

A view card's body can contain <eval>latest-of X</eval> or <eval>count-links-to X</eval>. The store never caches the resolved value; resolve_lazy re-evaluates on every read. That means a view written months ago surfaces the current store, not a frozen one. The lazy marker is intentionally plain HTML-ish syntax: easy to grep, easy to escape, easy to extend.

3 · Rules-as-cards — query rules the same way you query data

This is the single most important homoiconic property of the system. A rule is not a Python class or a config file entry. It is a card with :type "rule" and a :when / :then body. To find every rule that mentions "reverse" — store.find_by_type('rule') + substring filter on :body. To pause a rule — flip :status to "paused" and re-run fixpoint. In the demo (frog [4]), pausing r002_derived_from_reverse dropped the derived-card count from 99 to 46. The other 9 rules kept firing untouched.

"Rules-as-cards" has a second pay-off that is easy to under-appreciate: an agent can write a new rule mid-task. Authoring a rule means writing a card. The card goes through the same load path as everything else. The next call to run_to_fixpoint picks it up. Compare with a hardcoded rule engine where a new rule means a code change, a redeploy, a restart. Here it means one EDN write.

4 · Dedup restart protocol — conflict resolution as data

When a new card arrives that is 80%+ similar to an existing one, we don't crash and we don't blindly merge. We consult :on-dedup-conflict — a list of actions (keep-both, merge-prefer-newer, supersede) — and run the head. The trace (frog [5]) shows all three actions on the same 0.969-similarity pair, with the before/after store state captured.

5 · View cards — query-as-card, materialized at read time

A view card holds a query, not a result. store.materialize(view_id) runs the query now. The demo (frog [6]) materializes the "all sizing-lineage candidates" view three times — 14, 15, 14 — with a synthetic atom injected in the middle. The view tracks store mutation with zero coordination.

6 · Self-computing fields — confidence that updates with the graph

A claim card's :confidence is not a stored number but a (compute …) expression over inbound link counts. As supporting / contradicting atoms get added to the store, the same read of the same claim card returns a different number. The demo (frog [7]) walks through three stages: 0 → 1.0 → 0.333. No write to the claim card; the field is computed.

The honest version of this capability is: the kernel supports one specific shape of self-computing field — the supports/contradicts confidence DSL — recognized by pattern-match, not by a general s-expression evaluator. That is a limitation we documented but did not paper over. The architectural point still stands: computational fields are first-class data, and adding a second shape is a matter of writing one more pattern-match branch, not a rewrite of the kernel.

Engineering trade-offs we feel the weight of

Two design choices land differently than the prior arc's redesign HTML predicted; both are worth flagging because they will rear their head again as the system grows.

A · sexp as a surface form is great until the body needs to be markdown

The card body for an experiment is roughly the full markdown of the source paper — frontmatter, prose, math, double-link references, the lot. EDN handles that fine as a string literal, but escaping a 4 KB markdown body inside a sexp string is read-hostile: \n everywhere, and the EDN reader must accept embedded LaTeX $...$ and Obsidian-style [[link]] without choking. The Phase 1 parser is forgiving enough; the Phase 2 ingest writes 65 such bodies without issue. But the moment we want to edit a card body, the round-trip ergonomics drop. The intended fix (not implemented in this arc): store body as an external blob (:body-ref "path") and let the store join at read time.

B · the rule engine is a hash-of-triples, not a real index

RuleEngine.run_to_fixpoint iterates: for each rule, scan all atoms, attempt pattern match. With 11 rules and 3404 atoms, that's ~37k match attempts per iteration. Two iterations to fixpoint = ~75k. At 0.10 s that's fine. But scale to 100k atoms and 100 rules and we have a 10M-attempt loop. The textbook fix is a forward-chaining RETE network with alpha/beta nodes; we did not need it here. The shape of the indices we'd want is already visible: store.by_pred[pred] → list[atom_id] would cut rule-match time by ~30× immediately. We left it out because the trigger condition (perceived slowness) hasn't fired.

C · macros are dispatched by name, not by pattern

To run a macro the caller writes engine.expand("paper-to-experiment-suggestion", {"?source-paper": some_id}). There is no automatic "fire all macros whose :applies-to predicate matches this card." That would be a useful generalization — it would close the loop between the rule engine (auto-firing) and the macro engine (manually dispatched) — but it would also blur the line between "synthesis I asked for" and "synthesis that happened in the background." We chose the explicit dispatch for now, on the principle that an agent's first 100 cards should be ones it intentionally wrote.

D · the viz is a static layout, deliberately

Force-directed layouts can be interactive (drag nodes; re-run physics on hover) or static (run once, freeze). We chose static for two reasons. One, the 215-node default view is already at the visual budget where adding motion would obscure rather than clarify. Two, the goal of viz.html is verification ("yes the typed-link structure is real and the rules-derived edges land where we expect") not exploration. The 3331-atom view all toggle exists for spot-checking specific subgraphs; nobody is going to drag 3500 nodes around with a trackpad.

E · the kernel does not yet do versioning

Each card has :ingested_at and :source_mtime, so we can tell when something was last touched, but the store has no concept of "v2 of this atom". The current dedup-restart protocol is the closest thing — supersede wires a :superseded-by pointer — but a proper card-revision log (per-card history, blame for derived atoms) is not implemented. For a single-agent workflow this is fine; for multi-agent it will hurt.

What this leaves on the table

The kernel ships. Six capabilities work. That is not the same as "the vault is solved." A short list of things we did not do, in roughly the order I'd reach for them next:

  • Consolidation worker (sleep replay). Run a background pass that re-fires rules over the last N hours of additions and writes summary atoms; described at length in brain_memory_for_agent_wiki.html. Not implemented here.
  • Namespace partitioning for multi-agent. Today every card lives in one global :id space. Two parallel agents writing simultaneously would race. The fix is per-agent prefixes (agent-x/exp:…) and a merge step. Not implemented.
  • Retrieval subset for context budget. When an agent reads a card it currently gets the full body (often 60+ atoms-worth). We need a token-budget-aware retriever that picks just the typed-link neighborhood relevant to the question. Not implemented.
  • Full s-expression evaluator. The (compute …) field in cap6 is recognized by structural pattern-match — only the count-links-to %self … shape works. A general eval would let claim cards carry richer scoring logic. (See frog [7] and the known limitations block.)
  • Body-label canonicalization tail. 45 unknown body labels (90 warnings in phase2_ingest.log) remain unmapped. Each one is one more r001-style micro-rule; we did the high-frequency seven and stopped.
  • Lineage slug normalization for m002. The macro can mis-match a lineage when the source slug uses a different separator. Caught during Phase 4; documented but not patched.

None of these block dogfooding. They're the natural follow-ups for whichever agent picks up the next arc.

A note on what "dogfood" means here

The vault has been usable from Obsidian for weeks. What 260521a adds is a parallel, agent-readable surface — one an LLM-driven workflow can actually compute on without re-parsing markdown every time. The first dogfood test is whether the next arc's research agents (the ones that draft candidates, score them, and propose follow-ups) can talk to this store instead of grepping raw .md. If yes, every downstream agent benefits from the rules and macros we shipped here. If no, we'll know within one arc cycle, and the failure mode will tell us where the kernel's API is too thin.

A reasonable next checkpoint: rebuild one of the arc 260516a team agents on top of CardStore + RuleEngine and watch what queries it actually needs. Whatever predicates we didn't anticipate become the next round of r001-style canonicalizations. Whatever views it materializes repeatedly become candidates for a :cached hint. Whatever fields it wants to self-compute become the seeds of a proper s-expression evaluator. The kernel is shipped; the language is grown by use.

This arc is also a deliberate handoff. The redesign HTML from arc 260520a sketched 12 engineering problems and a 7-step migration plan; 260521a built five components, ingested one real vault, made six capabilities work, and wrote them down. Some of the 12 problems are now answered (homoiconic schema, forward chainer, idempotent reruns, viz, dedup); some are partially answered (provenance, namespace, lazy-eval); some are deferred (consolidation worker, retrieval-subset, multi-agent merge). The trail is the arc itself — arcs/all/260521a_wikify_auto_research_vault_sexp/ contains every step, with logs, EDN, traces, and visualization side by side. Read it as a single artifact rather than as scattered files.

(card "claim:cap6_c21_cross_stack_first_val_gate" :type "claim"

                            / (max (count-links-to %self :pred 'supports) 1))"
  :status "active")

stage b+3 supporter atoms → supports=3, contradicts=0 → (3−0)/max(3,1) = 1.000
stage c+2 contradictor atoms → supports=3, contradicts=2 → (3−2)/max(3,1) ≈ 0.333
Honest disclosure (mid-flight fix). resolve_lazy does not implement a general s-expression evaluator. It detects the specific count-links-to %self :pred 'supports / 'contradicts shape by structural pattern-match and dispatches to a hard-coded helper. A truly general evaluator (binding lookup, function dispatch, arbitrary nesting) is the most obvious next-step on the kernel; we left a TODO. Two observations from sitting in this REPL for ten minutes:

  • The "everything is a card" promise pays off the moment you want to mix rule-derived facts with original atoms in a single comprehension. find_by_type returns both via the same iterator; the consumer cares about :pred, not where the atom came from.
  • The bottleneck is not any single query — it's knowing which predicates exist. store.predicates() returns a frequency-sorted dict (which we built mid-session and didn't ship as part of the kernel API). That's the next ergonomic addition.

All queries above run in < 50 ms on the loaded store; the slowest step is the initial CardStore.load_dir (about 0.4 s for the full union). Indexes would be a 30× speed-up on the load step, not on query. The Q3 case in particular surfaces a subtle property worth highlighting: r003_competes_with_symmetry emits the reverse edge as a separate derived card, not as a mutation on the original atom. So one declared competes_with in the vault becomes two facts in the store — one with :type "atom" (the original) and one with :type "derived" (the closure). Both are returned by find_by_type('atom') only if the query uses find across types; otherwise the consumer needs to remember to ask both. This is the exact place where "everything is a card" stops being free.

Known limitations · honest list

  • cap3 string filter on :body is "reverse" not "反向". The original prompt said the substring check should match Chinese "反向"; in practice the rule bodies are written in English ("reverse edge" / "without a reverse scan"), so we matched on "reverse". Two hits as documented.
  • cap4 similarity uses :body mirror, not :obj. The Phase 4 spec briefly proposed comparing atoms by :obj; in real atoms the :obj for section-text atoms is short (the section title), so we mirror the body into a comparable surface and run similarity on that. Result: 0.969 on the constructed pair.
  • cap6 confidence DSL is pattern-matched, not parsed. See frog cell 7. The only recognized shape is (compute (- (count-links-to %self :pred 'supports) (count-links-to %self :pred 'contradicts)) / (max (count-links-to %self :pred 'supports) 1)). Anything else falls through and the field stays as-is.
  • m002 lineage slug normalization. The macro joins on the literal lineage ID; if a card's parent_lineage uses a slug variant (e.g. different underscore convention), the macro misses it. The eight current lineages all match cleanly, so this didn't bite in the demo.
  • 90 unknown-body-label warnings. Captured verbatim in output/phase2_ingest.log. 45 distinct labels; we canonicalized the seven highest-frequency. The rest remain queryable as atoms with their original predicate name.
  • List-typed atom slots hardened in-memory only. 53 atoms had list values in :subj / :pred / :obj slots from the YAML axis: [sizing] form; the loader coerces them to tuples in memory but does not rewrite the on-disk EDN. A re-serialize pass would close that gap.
  • Tag-axis atoms are flat, not hierarchical. The vault tags like axis/sizing imply a two-level taxonomy (axis namespace + leaf); we store them as flat strings (has_tag "tag:axis/sizing"). Queries like "all atoms under any axis/*" need a prefix scan, not an indexed lookup.
  • No transitive closure short-circuit. Rule r004 (falsifies_cluster) walks two falsifies hops; on the current vault that's zero hits because the falsifies chain isn't long enough. If the chain grew to length 5, r004 would emit O(n²) derived atoms on each pass. A length cap is the natural guard; we did not add one.
  • The viz doesn't visualize rule cards. Rules and macros appear as nodes if their :id is referenced by a derived atom's :derived_from, but the rule's own :when / :then structure isn't drawn. A dedicated rule-viz pane is on the list.
