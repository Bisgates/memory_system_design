LLM-Wiki 规则引擎最小可运行原型

一份让 agent 真的"读规则、写规则"的 wiki 怎么会长成这个样子——从 form 反推回 force，再用一组真实数字去试它的脆点。
arc 260520a · 2026-05-20 · bird · 鸟瞰
I · 提问

如果 agent 自己维护 wiki，"维护"到底是什么？

把所有关于"个人知识库"的工程话术先剥掉，剩下的题面其实只有一句话：一个长得像 markdown 仓库的对象，每天有新材料进来，agent 要让它整体保持自洽，且让每一次新材料的接入都把过往的价值放大一些。听起来温和，工程上却是七十年没人扛得动的活——所有人写到几百页就放弃，不是因为读不动了，是因为维护交叉引用、同步综述、标注矛盾这件事的成本曲线比内容曲线陡。

所以问的不是"怎么搭一个 wiki"。那是工具问题。问的是：当人不再做这份 bookkeeping 之后，那份 bookkeeping 真正的形状是什么。它如果只是"把若干段文字写到若干份文件"，LLM-wiki 就退化成一个比 RAG 漂亮一点的散文生成器——每一份新材料让 wiki 的总价值线性涨一点，每一次 query 又得重新拼接。这不是 wiki，这是更省力的搜索。

朴素方案 · 它为什么不够

最自然的写法：LLM 拿到新源，写若干个 markdown 文件，更新 index.md，append 一行 log.md。能跑。但规则藏在 prompt 散文里——"看到新人名就建 entity 页"、"看到 contradiction 就标记两边"——它们没有结构、不可独立触发、不可单元测试、不可 retract 单条。等 prompt 长到三千字，agent 就开始失忆，wiki 也开始失自洽。

把这件事押在更尖的形上：我们要找的，是一个让 wiki 的价值乘法而不是价值加法的抽象。每加 1 个源能触达过去所有源；每加 1 条规则能回溯吃过去所有源。N 源 × M 规则 → 至多 N·M 条关系。如果只能做到 N + M，那就是失败。

朴素 wiki · 加法

每个源最多触达几页相关页。Agent 写完这一页就走。维护成本 ∝ 内容量；过半年没人想动它。

规则引擎 wiki · 乘法

规则升格成一等数据。每加 1 条规则在过去所有原子上回溯派生；每加 1 个源让所有现存规则都跑一次。结构性放大。

这是问题的形状。它不是"该用 lisp 还是 python"，也不是"该不该上 vector store"——那些都是底下的选择。真正的 leverage 在于：能不能让 agent 的主产物从"页"变成"规则"。

Agent 的产物如果还是"散文"，wiki 永远是线性的。
把产物换成"规则"，它一夜之间就有了第二个维度。
II · 原子

事实的最小形状

先把"facts"这件事推到极限。如果一份 wiki 里所有的"事实"都长一个样，那个样子最少要带几个字段？把它推到 0 个，全是自由文本——就回到 RAG。推到 ∞ 个，每条 fact 都是一个完整的关系数据库表——你失去了 markdown 的 ergonomic。在这两个极端之间，有且只有一个稳定的最小形状能让 forward chaining 跑得动而不爆炸：三元组 + provenance。

三元组 (subj, pred, obj) 来自一个非常古老的传统——RDF / Datalog / Datomic 都把它当原语——理由都一样：它是"能被 pattern 匹配的最小语义单元"。少一项变 unary（"事实的内容"找不到落点），多一项变 quad/quint（你不得不给每个 slot 起一个名字，DSL 复杂度 explode）。把这层抽象放回到 markdown 域里：

id: a_a26feb5c             # stable hash of (subj, pred, obj)
subj: arc:260508b          # 跨 namespace 的 symbol
pred: introduces_doc       # 一个固定词汇表里的动词
obj:  doc:notes/lidar_merge_quality_metric.md
source:       arcs/all/260508b_l2_lidar_merge_metric/9_summary.md
derived_from: null         # null = extracted; 否则 = rule_id
parents:      []           # 仅 derived 时非空

source 和 derived_from/parents 这一组字段不是装饰。它是整个抽象的承重柱。少了它们，wiki 就退化回"一堆事实"，撤回一条 bad rule 时无法逆向；多了它们，每条原子都是它自己的 git diff，retract 一条规则 = 删 markdown + 重跑 = 它派生的全部 atoms 自动消失。这是 event sourcing 的味道，但事件粒度细到了三元组级别。

asymptotic check

把 derived_from 去掉会怎样？答案是：你立刻失去 chain 的可调试性——一条 derived atom 不知道是谁派生的，撤一条规则就要全量重跑而不能局部修。把 parents 去掉会怎样？你失去了 viz 反向链——"这条结论从哪些事实里来的"这件事不能在 1 ms 内回答。两个字段都不能省。

命名空间约定

每个 subj/obj 以 ns:id 形式存在——arc:260508b、doc:notes/foo.md、code:utils/x.py、topic:lidar、type:arc。这件事看着小，实际它让 pattern matching 不用 schema 也能正确分轨——(?A, mentions_code, ?C) 自动只跟 code namespace 的 obj 对上。Datomic 里也是同一招。

这一节的元反思：当你能把"事实"压到这个粒度，wiki 的 mutable state 就从"段落"降到"三元组"——它成为可组合的对象，而段落永远不可组合。

III · 规则

让规则也是 wiki 的一页

原子是事实，规则是从事实到事实的函数。Norvig 在 PAIP 里有一句话："Lisp 派 30 年来一直坚持的同一个论点是 schema 即数据"。把这句话扣到 wiki 上的代价非常便宜——规则只要也写成一份 markdown，agent 就能 lint 它、grep 它、版本化它、单测它、删掉一条 retract 它。规则 = page，而不是"prompt 的某一段"。

每条规则的形状大致就这么多：

---
id: r002_doc_used_by_arc
when:
  - {subj: "?A", pred: introduces_doc, obj: "?D"}
  - {subj: "?B", pred: mentions_doc,   obj: "?D"}
constraint: "?A != ?B"
then:
  - {subj: "?D", pred: used_by_arc, obj: "?B"}
---
# r002 · 复用监测：doc 被引入后又被其他 arc 提到
A 引入 D，B 也提到 D（B≠A）→ D 被 B 复用。
被 r009 链式消费（co_used_with）。

frontmatter 是可执行的部分——agent 不写 prose 解释自己的规则就 prose 解释；它通过 frontmatter 把 pattern 交给引擎，body 留给人和 agent 自己读。Pattern 的语法刻意做到只有三件事：conjunction、变量 bind、constraint。没有否定，没有聚合，没有算术。这是 Datalog 的子集——够用就停。每加一条 DSL feature 都得付 termination 复杂度的钱，不挣钱不加。

cross-domain transfer

"规则即数据"这个形状以前出现过至少四次——每一次背后的抽象理由是同一个：

make · 构建系统

foo.o: foo.c 是 pattern；$(CC) -c $< 是 action。Makefile 自己是 makefile 的输入。

Datalog · 演绎数据库

事实集合 + Horn 子句 + fixpoint。1985 年就把这件事的语义封死了。

Event sourcing · CRDT

状态 = 折叠（事件流）。事件是只追加的事实；折叠规则是可演化的代码。

Emacs / Org · 自描述编辑器

同一个 buffer 既是数据又是程序。C-x C-e 在原地求值——schema 改 schema 的最纯实现。

四个不同的领域都收敛到了同一个 shape——这是 Hamming 反复说的"同一个数学结构在不同伪装下反复出现"——LLM-wiki 是第五个，区别只在于 eval 是个概率函数而不是确定函数。但 form 完全一样。

这一招要发生，要付的代价

放弃 turing-完备的 DSL。放弃在 rule body 里写代码。放弃 negation。放弃聚合。换来的是：fixpoint 一定收敛、每条规则可单测、每条规则可独立 retract。这是非常划算的交易——但只要你试图加 negation，整个抽象就开始漏水。

IV · 引擎

forward chaining 是这个抽象唯一允许的计算

有了原子和规则，"跑 wiki"是什么意思？严格地讲，只能是一件事：把所有规则在所有原子上反复匹配，把每次匹配派生出的新原子加进去，直到没有新原子可加。这是不动点。不是优化、不是策略选择——它是这个抽象唯一允许的计算。换句话说，引擎的设计从抽象里掉出来，不是被设计出来。

核心循环大概十行：

def run(atoms, rules, max_iter=20):
    store = AtomStore(atoms)
    while True:
        added = 0
        for rule in rules:
            for binding, parents in match_all(rule.when, rule.constraint, store):
                for tpat in rule.then:
                    new = instantiate(tpat, binding, rule.id, parents)
                    if store.add(new):  # dedupe by (subj, pred, obj)
                        added += 1
        if added == 0:
            break
    return store

"由不动点掉出来"的另一面是必然 idempotent。store.add 用 (subj, pred, obj) 的 hash 去重，所以重跑一万次和重跑一次结果完全一样。这件事重要到值得停一秒：在一个 LLM-参与的环境里，输入是 stochastic 的、prompt 是 mutable 的，整套机械化部分必须是 idempotent 的，否则你没有办法 reason about state。

semi-naive 的小诡计

实现上有一个不显眼的工程选择：同一 iteration 里，后跑的规则可以看到前跑的规则在本轮派生的新原子。这违反了 strict naive forward chaining 的语义（应该等本轮所有规则跑完才更新 store），但代价是测出来的 iteration 数字变得没意义。我故意选了 semi-naive——因为收敛速度更快、产物完全一样、且实测上 fixpoint 在 2 iterations 内就到。Datalog 的标准实现也是 semi-naive。

为什么不要做"smarter"的引擎

在 200 行代码 + 30 sources 的尺度上，聪明的索引带来的省时不抵代码复杂度的代价。引擎要么停在 naive forward chain（≤200 行）、要么直接上 Datalog 编译器（≥ 3000 行）。中间形态都是输。

这一节的元反思：当你的 wiki 形状选对了，计算就不再是 design space 的一个维度——它变成了 form 的一个推论。这是"abstraction collapse"最爽的一面——不止设计变薄，设计选择本身也少了一层。

V · 链

为什么这一切到这里才开始变得有意思

到目前为止描述的东西，是一个三元组数据库 + 一个 Datalog 引擎——挺老的技术。真正的新意——也是这次 arc 想押的东西——在于 chain：一条规则的派生原子可以被另一条规则消费。这是 forward chaining 在 LLM-wiki 场景里的真正杠杆，它是"价值乘法"的微观机制。

把规则分成两类。第一类是 extracted-only join——只匹配 ingest 阶段抽出来的原始事实。第二类是 chain rule——它的 when 里至少有一个 predicate 是别的规则派生出来的。把这两类摆并排：

extracted-only join · r007

has_topic(?D, ?T) + has_topic(?E, ?T) → shares_topic_with(?D, ?E)。两个槽都吃原始事实。yield ∝ Σ_T (N_T choose 2)，topic 越热 yield 越大。

chain rule · r009

used_by_arc(?D, ?B) + used_by_arc(?E, ?B) → co_used_with(?D, ?E)。消费 r002 派生。yield 完全被 r002 的输出尾巴卡住。

chain rule 的价值在于"每加 1 条 chain rule，理论上释放 N·M 的潜在边"。它不是直接读源，是读"规则读源之后的产物"——它在做语义层面的二阶组合。这件事其它范式里非常难表达：散文 prompt 里你没法 cleanly 说"消费上一条 prompt 的结论"；vector store 里则根本不存在"派生事实"这种东西。

kernel_v3 四招都掉出来了

这件事是这次 arc 最值的发现：之前那个 alpha_second/kernel_v3 分支里 4 种 lisp-pro 招（macros / multimethod / condition-restart / lazy streams）原本是各自独立的机制；放到这个 rule-engine 抽象里，它们全部从一个机制里掉出来。一对一对应：

kernel_v3 招在 rule engine wiki 里的对应物
homoiconic sexp + macro规则就是 markdown 页；规则可以匹配规则（meta-rule，schema 自描述）
CLOS multimethod规则的 when pattern 就是多轴 predicate；新源类型 = 新规则（一文件）
condition / restarthas_duplicate_introducer 这种 derived atom 是结构化矛盾；用户的"skip / merge / branch / supersede"选择是写回引擎的另一条规则
lazy stream sharingforward chaining 本身就是"一份事实，多条规则同时消费"——一次 extract 喂 N 条 chain

这才是"kernel_v3 神迹"的真正复现——不是把四招迁移过来，是找到一个抽象，让四套独立机制变成同一套机制的不同侧面。这是 Hamming 反复在 "Coding Theory" 一讲里说的那种现象——若干个不同的工程构件，背后是同一个数学结构在作怪。

四个机制坍缩成一个机制。这不是设计上的胜利，是发现上的胜利。

这一节的元反思：当你看到不同领域的若干个 mechanism 都开始向一个 shape 收敛，停下来——你大概率正站在一个更深的抽象的边缘。push 它，把那个抽象写出来；不要满足于"我注意到这件事"。

VI · 实验

把数字砸到形上看它的脆点

抽象漂亮不算数，得让它顶着真实数据跑一下。30 份 3dgs 项目源（8 arcs / 14 notes / 2 decisions / 1 paper / 5 specs），10 条手写 seed rules + 1 条 chain² ablation r011。359 个 atoms，211 条 derivations，跑 26 ms。下面是没有被美化过的四张验收卡：

L1 指标目标实测判定
10 条规则总 derivation 数≥ 50209PASS
第 11 条规则边际增益≥ 52FAIL
引擎全量 wall time< 5 s26 msPASS
spot-check 抽样有效率≥ 30%manual—

L1.2 没过。要说清楚是为什么不过——而不是把数字往好处粉饰。

断在哪里

每条 rule 的产量分布是这样的：

r007_doc_co_topic_neighbor      152   <- dense join, extracted-only
r004_code_developed_in_arc       21
r001_introduces_reverse          15
r005_arc_contributes_topic        6
r002_doc_used_by_arc              5
r003_arc_ref_reverse              4
r006_arc_depends_on_older_arc     4
r008_duplicate_introducer         0   <- 数据里就没有矛盾，这是项目质量信号
r009_co_used_with                 2   <- chain consumer of r002
r010_topic_shared_arc             0
r011_ablation_strong_neighbor     2   <- chain² consumer of r009 + r007

看尾巴。chain² 被卡死了，但不是被 chain 机制卡死，是被上游稀疏卡死：r002 只产 5 条 used_by_arc，r009 继承到 2 条 co_used_with，r011 在 r009 ∩ r007 上做 join 只能拿 2 条。这是数据规模问题，不是抽象问题——但抽象层面的教训仍然是真的：chain 的价值高度依赖上游高 cardinality。

但同时这件事告诉我们另一面：aggregate 的乘法效益其实成立。avg 19.2 derivations/rule，比线性 baseline 大 19 倍。"指数微分"在 aggregate 层面没问题；只是在 chain² 这条特定 ablation 上需要密集上游。

r008 = 0 不是 bug，是体检报告

contradiction-lint 规则在 30 份源上派生了 0 条——意思是项目里没有任何"两个 arc 都声称 introduces 同一份 doc"的情况。这条规则就是为这种矛盾存在的；它输出 0，本身是结论。这种"用规则把不存在的东西显式化"的体检属性，朴素 wiki 完全做不到。

asymptotic 推演

把 source 推到 0，aggregate yield 当然归零——退化成空 wiki。把 source 推到 ∞（或者只要 ≥ 50 arcs），r002 类规则上游变密，r009/r011 链条就活了——chain² 的 marginal 应当从 2 上升到几十。这意味着：这次 L1.2 的失败不告诉我们 chain 不 work，它告诉我们 chain 在这个数据规模下还没开始 work。

一个抽象在小数据上的失败，往往不是抽象错了。
它是在告诉你这个抽象的"启动门槛"在哪里。
VII · 收

这次坍缩留下了什么

最后这一段不打算总结全文——总结上面六章已经够了。它只想留三件等以后细节都忘掉之后还应该记得的事。

形状先于实现

整个 arc 的成本，集中在一件事上：把抽象坍缩到 (atoms, rules, fixpoint) 这三个名字。一旦这三个名字定下来，引擎是 80 行，DSL parser 是 80 行，ingest 是 120 行，viz 是 200 行——加起来不到 600 行。"难"的地方不是写代码，是认出 chain 是 rule-engine 的真承重柱，而不是 lisp 同像性、不是 markdown 语法糖、也不是 LLM 智能本身。

chain 是真承重，但有启动门槛

chain 让"加 1 条规则放大 N 条原子"这件事可能；但它需要上游 dense。在 30 sources × 11 rules 这个规模上，chain² 还没真正 fire。下一步的工作不是改引擎，是增加 sources，或者设计能把 dense rule 当 upstream 的 chain rule。后者就是用 r007 (152) 当 chain 的源头，而不是 r002 (5)。

不要把"指数"喊太响

实测上"指数"在 aggregate 层面成立，在 chain² 层面这个数据规模下不成立。诚实地这么写——而不是把 avg/rule 那个 19.2 拿出去当 marketing 数字。这条抽象的真正杠杆点是 chain；chain 的瓶颈是数据稀疏。未来的所有讨论都该围绕这件事，不该被 aggregate 数字遮住。

EDITOR'S NOTE · meta-reflection

什么时候你才知道找到了正确的抽象？

答案不是"代码变少了"——那只是症状之一。真正的信号是：原来若干个独立的机制开始从同一个机制里掉出来。kernel_v3 的四招在这次 arc 里坍缩成 "rule + forward chain" 一件事；Datomic / Datalog / make / Emacs 这四件看起来不相关的工程在背后共享同一个 form——这是抽象正确的最强信号。但抽象正确不等于立刻就 work。它告诉你向哪走，不告诉你已经到了。这次的 L1.2 = 2 是温柔的提醒——形状对了，但数据规模还差一点。

第一反应是 "让 LLM 每次写完 arc 之后顺手更新 wiki 页"。但这条路有一个不会自愈的故障模式：agent 的产出是页面，而页面 N+1 篇里有 N 处会被 N+2 篇的某个细节悄悄推翻 — 没人审，长出来就老化。agent 产页面 = 不可维护。

所以我们换个产物：让 agent 产规则。规则少（一两百条）、可 grep、可 diff、删一条它派生的链接就消失。页面只是 (atoms × rules) 的派生投影。

stop & think

这个 reframe 的赌注是：100 条规则 × 1000 条 source ≈ 100k 条关系，而每条规则一次写好可以反复用。如果做不到这一点 — 也就是规则之间不组合，N×M 退化成 N+M — 那这个抽象就破产。本 arc 就是要在 200 行 Python 里把这个赌注的成败实证出来。

In [4]: utils/atom.py（核心 dataclass）
def _atom_id(subj: str, pred: str, obj: str) -> str:
    h = hashlib.sha1(f"{subj}|{pred}|{obj}".encode("utf-8")).hexdigest()[:8]
    return f"a_{h}"

@dataclass(frozen=True)
class Atom:
    subj: str
    pred: str
    obj: str
    source: str = ""
    derived_from: Optional[str] = None
    parents: tuple = field(default_factory=tuple)

    @property
    def id(self) -> str:
        return _atom_id(self.subj, self.pred, self.obj)

    @property
    def key(self) -> tuple:
        return (self.subj, self.pred, self.obj)
stop & think

等等 — 为什么要把句子切成三段 (subj, pred, obj)，而不是直接写 "260508b 这个 arc 引入了 lidar_merge_quality_metric.md"？

答案藏在第三章。三元组的形状决定了规则可以写成"当存在 (?A, introduces_doc, ?D) 且存在 (?B, mentions_doc, ?D) 时，派生 (?D, used_by_arc, ?B)"。自然语言版本里 ?A / ?D / ?B 不存在 — 没有 hole 就没有 join。RDF 切法是为了让 pattern matcher 能工作。

另外注意 id = sha1(subj|pred|obj)[:8]：同一个事实重抽 / 重派生都不重复入库（dedupe-by-content）。parents 是反向链 — 派生 atom 知道它从哪两条父 atom 来的。

In [md]:

项目根上 31 篇 markdown 跑完，extract_atoms.py 吐出 359 条 atom。整个抽取过程零 LLM、零网络、毫秒级。这一步的成本几乎为零，意味着 source 再加一倍，atoms 也只是线性涨 — 这是后面"乘法"成立的前提：atoms 是廉价的事实层。

[III] 规则：每条规则是一份 markdown

In [md]:

看一份完整的、跑在真实数据上的规则。这是 11 条规则里的第 2 条，output/260520_2102_demo_run/wiki/rules/r002_doc_used_by_arc.md：

In [5]: cat r002_doc_used_by_arc.md
---
id: r002_doc_used_by_arc

  - {subj: "?A", pred: introduces_doc, obj: "?D"}

# r002 · 复用监测：doc 被引入后又被其他 arc 提到

A 引入 D，B 也提到 D（B≠A） → D 被 B 复用。
这是整个 wiki 里"知识在跨 arc 流动"的硬证据。

被 r009 链式消费（co_used_with）。
In [md]:

这是规则 DSL 的全部。一行一行拆：

  • id — 规则的稳定标识，也是派生 atom 的 derived_from 字段。
  • when — 一个三元组合取式（AND）。每个槽位可以是字面量（introduces_doc）或变量（?A，问号开头）。同名变量在整个 pattern 里共享 binding — 这是 join 的语义。
  • constraint — 一个被严格白名单的 Python 表达式（只允许 == != < > 等比较），bind 后求值。这里 ?A != ?B 排除"自己引入自己也提到自己"的退化解。
  • then — 一条或多条 emit 模板。规则 fire 一次 → 每条 then 派生一个 atom。

body 是给人看的：说明语义、预估 yield、写明被哪条下游规则链式消费。r002 这一段尾巴上写着 "被 r009 链式消费" — 这就是第三章的 chain。

In [6]: utils/rule.py — Rule.from_markdown(path)
@classmethod
def from_markdown(cls, path: str | Path) -> "Rule":
    p = Path(path)
    text = p.read_text(encoding="utf-8")
    if not text.startswith("---"):
        raise ValueError(f"{p}: missing frontmatter")
    _, fm, body = text.split("---", 2)
    meta = yaml.safe_load(fm)
    rule_id = str(meta["id"])
    when = [Pattern.from_dict(x) for x in meta["when"]]
    then = [Pattern.from_dict(x) for x in meta["then"]]
    constraint = meta.get("constraint")
    if constraint is not None:
        constraint = str(constraint)
        if not _SAFE_CONSTRAINT_RE.match(constraint):
            raise ValueError(f"{p}: unsafe constraint chars: {constraint!r}")
    return cls(id=rule_id, when=when, then=then,
               constraint=constraint, source_path=str(p), body_md=body.strip())
DSL 边界

明确不支持的 — negation（"没有 X 时…"）、aggregation（count / sum / max）、算术、disjunction（OR）。conjunction + bind + emit 三件套，够用即停。这条约束让规则可单测、可 grep、可 lint；也让 engine 100 行写得完。Datalog 的最小子集，没什么神秘的。

In [md]:

类比：你写过 PyTorch 的 nn.Module，每个 module 是一份独立、可序列化、可组合的 spec；这里的 rule 是同样的意思 — 一份独立、可序列化、可组合的"推理单元"。或者更近的类比：make 的 rule（target: deps; recipe），或者 SQL 的一个带 join 的 view。这条规则 = 一个 view definition。

[IV] 引擎：100 行的不动点

In [md]:

有了 atoms（数据）和 rules（pattern → action），剩下的就是把 rules 反复扫在 atoms 上直到不再产生新东西。这是 forward chaining 经典套路：每轮所有规则都 fire 一遍，新派生的 atoms 进入 store；下一轮这些新 atoms 又会被消费它们的规则匹配到。直到一轮过去 zero new atoms — 收敛了。

In [7]: utils/engine.py — run() 主循环
def run(initial, rules, *, max_iter=20) -> RunResult:
    store = AtomStore()
    extracted = 0
    for a in initial:
        if store.add(a):
            extracted += 1

    trace, per_rule = [], {r.id: 0 for r in rules}
    iteration = 0
    while iteration < max_iter:
        iteration += 1
        added_this_round = 0
        for rule in rules:
            for binding, parents in _match_all(rule.when, rule.constraint, store):
                for tpat in rule.then:
                    triple = _instantiate(tpat, binding)
                    if triple is None: continue
                    subj, pred, obj = triple
                    new = Atom(subj=subj, pred=pred, obj=obj, source="",
                               derived_from=rule.id,
                               parents=tuple(p.id for p in parents))
                    if store.add(new):                # ← dedupe-by-key
                        per_rule[rule.id] += 1
                        added_this_round += 1
                        trace.append(DerivationStep(
                            iteration=iteration, rule_id=rule.id,
                            binding=dict(binding),
                            parents=tuple(p.id for p in parents),
                            derived=new))
        if added_this_round == 0:                     # ← fixpoint reached
            break
    ...
In [md]:

三个细节值得停下来看。

(a) store.add(new) 返回 bool：(subj, pred, obj) 已经在 store 里就返回 False，added_this_round 不增。这是 dedupe，也是不动点终止条件的物理基础 — 因为我们的 then 只 emit，从不删除，新 atom 集是单调递增的，又有上界（所有可能 subj×pred×obj 的有限组合），所以必然收敛。

(b) derived_from + parents：每个派生 atom 都记得是哪条规则在哪个 binding 下从哪几条父 atom 派生出来的。viz 反向链就靠这两个字段。这跟 PyTorch autograd 的 grad_fn + next_functions 是同一个意思 — backward 的时候沿着这条链回溯。区别只是这里 forward 一次到底，没有 backward。

(c) _match_all 是递归：对 when 里的每个 pattern 逐个尝试匹配，已 bind 的变量在后续 pattern 里被替换成具体值，没 bind 的变量在 candidates 中遍历。这等价于 nested loop join。

In [8]: utils/engine.py — _match_all（递归 join）
def _match_all(when, constraint, store):
    def step(i, binding, parents):
        if i == len(when):
            if constraint and not eval_constraint(constraint, binding):
                return
            yield binding, parents
            return
        for b2, a in _match_one(when[i], store, binding):
            yield from step(i + 1, b2, parents + (a,))
    yield from step(0, {}, ())

[V] 链：rules × atoms 的乘法

In [md]:

整个抽象的赌注都在"规则能不能链式组合"。如果不能，加第 N+1 条规则只能从原始 atoms 里榨油，yield 是常数；如果能，第 N+1 条规则可以站在前 N 条派生的 atoms 上 — 它的输入越用越多。

第 9 条和第 11 条规则就是为这个验证故意设计的。先看 r009：

---
id: r009_co_used_with

  - {subj: "?E", pred: used_by_arc, obj: "?B"}

# r009 · 同被一个 arc 复用的两个 doc → 互为复用邻居 (CHAIN)

**消费 r002 的 derived atoms**（used_by_arc）—— 第一条 chain 规则。

如果 r009 在 baseline 跑里贡献了非零数字，说明 forward chaining 真的发生了。
如果它是 0，说明 r002 的 yield 集中在"同一 arc 只复用一个 doc"，rules 没有组合
— 需要重新设计。

被 r011 (ablation) 链式消费。
In [md]:

r009 的 when 里有 used_by_arc — 注意 extract 阶段从不产生这个 pred，它只能来自 r002 的 then。也就是说 r009 fire 的前提是 r002 先 fire 过。这是 chain¹。

r011 更激进 — 它把两条都派生而来的关系合取（chain²）：

id: r011_ablation_strong_neighbor

# r011 · ABLATION · 同时 co_used + shares_topic → strong_neighbor (CHAIN²)

**这条是 ablation：第 11 条 rule，它消费 r009（chains r002）AND r007 的输出**。
两个 derived predicate 的合取。

如果它贡献 ≥ 5 条 derivations → "rules × atoms 乘法效益" 成立。
如果它 < 2 条 → 规则之间不正交也不组合，N×M 退化成 N+M，整个抽象证伪。
In [md]:

r011 同时消费 co_used_with（来自 r009，r009 来自 r002）和 shares_topic_with（来自 r007）。两条派生 pred 都得对上同一对 (?D, ?E) 才 fire。这条规则必须站在派生层上 — 它的原料一行都不在原始 atoms 里。

[VII] 教训

In [md]:

一个 collapse、一个失败、几条小心得。

collapse：把 wiki 维护问题压成 (atoms, rules) → derived 的纯函数后，agent 的工作量从 N×M 降到 N+M — agent 只需要维护几十到几百条规则，而 sources 用确定性 regex 抽。规则是一等公民：可 grep、可 diff、可单测、删一条它派生的所有连接随之消失。撤销 = git revert + rerun。

失败：strict marginal acceptance（rule 11 ≥ 5）没过，但是好的失败 — chain 跑通了，trace 闭合，瓶颈精确定位在 source pool 太小。如果未来 source 数翻倍 / 翻十倍这条线就会过；不需要重写抽象。

小心得

  • regex extract 在富 markdown 上能撑住，但 00_index.md 这种 catalog 必须排除，不然 mentions_doc 会被 index 大量污染。extract_atoms.py 里 INDEX_FILES = {"00_index.md"} 这个集合的存在是被实际跑出来逼出来的。
  • constraint 用白名单 regex + eval 是不优雅的，但够用，且只发生在 trust 自己写的 rule.md 上 — 不能允许 LLM 自由 emit constraint 字段，否则有 sandbox 逃逸。下一轮如果让 LLM 写 rule，constraint 要换成 AST allowlist。
  • 不动点 ≤ 5 iter 是 forward chaining 的常见情况 — 因为 chain 长度等于规则的 max depth，本 arc 最长 chain（r002 → r009 → r011）刚好 3 跳，所以 2 个 iteration 就够了。
